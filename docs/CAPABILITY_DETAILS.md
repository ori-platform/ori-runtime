# Capability Details

The full notes behind the rows of `docs/CAPABILITY_MATRIX.md` whose summary links here. Each section is the capability's record of what is implemented, how it was proved, and what remains unverified. Update a section when its capability changes, and keep the matrix row's summary true.

## Tier A/B/C/D dispatch

Status: Implemented. Files: action_dispatcher.py, dispatch_plan.py, dispatch_coordinator.py, resource_gate.py, rule_engine.py, elevator.py.

All four tiers, asyncio.shield for Tier D. `executed` on an action row means an executor ran and reported success: a dispatched action with no registered executor is a non-execution at every tier, recorded as `no_executor` and distinguishable from an executor that ran and failed. A governed action reaching dispatch without an executor is logged at error. **Which trigger fires is no longer decided by declaration order.** For one event every skill *eligible for that event* — those declaring its sensor type, decided by the same function the loader subscribes from — is evaluated exhaustively and the full set of matched triggers is assembled before any reasoning task is scheduled, so a Tier D match anywhere in that set is attempted before lower-authority work anywhere in it. Tier D conditions read the reading and the skill's configuration only, so they are decided and attempted before any skill hook runs and before any history is read from the store; the loader refuses a Tier D condition naming anything other than the reading's fields and the skill's packaged configuration, and the rule engine refuses one it cannot resolve. Synchronous skill hooks run on one dedicated daemon thread, never the event loop or its default executor, fed by a queue of four and awaited for two seconds; a hook that is queued past that, or runs past it, is skipped for its reading, the triggers needing its output are not evaluated, and stop abandons a stuck hook after two seconds and counts it lost. A hook still queued at its deadline never starts, and a hook's skill-state writes are held and committed only with a result accepted in time, so a skipped, late or abandoned hook persists nothing. Hooks are synchronous: an asynchronous hook is refused at load and never run on the loop. A Tier D incident's work never waits on a hook, including its post_reasoning text. Hook store calls use a connection owned by the calling thread, never the writer's, with a 50 ms busy timeout and a one-second fail-fast window after a lock. Previously the rule engine returned the first match in declaration order and the elevator selected a winner by comparing that one name against the handler's own trigger, which was blind to tier and silent: a Tier D trip declared below a Tier A trigger on the same condition never fired, and a Tier C proposal below one was never raised. **Each action in a plan is dispatched at its own authority, not the trigger's.** An action the registry proves inert — an A floor that is not physical — is Tier A; an action that is the commissioned protective outcome the safety condition licenses, with every clause of the Tier D grant holding, is Tier D; everything else is `min(C, max(registry floor, declared tier))`. Nothing inherits authority from the incident, so a notification accompanying a trip is Tier A and a Tier C plan's notification is sent with no approval round trip. Because an action row is sealed on the tier it was dispatched at, a notification in a Tier D plan is no longer recorded in the evidence chain as a safety-critical action. The Tier D grant is six clauses and is granted to one outcome on one resource, never to an action name or a plan: a Tier D incident, `bypass_llm`, a first-party skill, the action resolving to the commissioned protective outcome on a zone the condition covers, the trigger's own defaults naming it, a non-informational action, and a registered executor. An action failing the outcome clause is not refused — it runs at its own authority, capped at Tier C. The registry holds no physical name without an executor behind it: `emergency_cutoff`, `open_safety_circuit` and `switch_power_source` were retired rather than bound, because a physical capability is an outcome on a commissioned zone and not a name, and a source-check test now fails if a physical entry is ever governed that `OriRuntime` never registers. The three actuator-specific names that remain are the legacy set `safety-profile/v1` carries as normative vocabulary, each resolving to one protected-circuit outcome; `close_gas_valve` in particular stays until the gas condition migrates into its profile under the ratification-gated cutover, because the contract states that path and a rename now would be a second, undocumented one. New physical capability arrives as an outcome defined in the specs and bound by commissioning, never as a registry name. The commissioned binding composes with the registry floor and may raise it, never lower it; a binding claiming an act is more reversible than the registry says is a commissioning error and is reported. An action that requires a commissioned zone and has none is not dispatched at all, and an action the registry does not govern is refused at admission rather than dispatched and left to fail at a missing executor. **Physical acts are admitted against the resource they drive, never their name.** One runtime-global gate keyed on the zone's identity holds an in-flight record per resource — the admitted outcome, the tier, the contributing triggers and how far the attempt has got — so the same outcome coalesces into one executor call with a coalescing record while the opposite conflicts. Precedence depends on the holder's state: a reservation not yet started is preempted by a higher tier and both are refused at equal tier; an action that will ask an operator is admitted as a proposal under the same lock as the admission rather than marked afterwards, so a Tier D arrival cannot see a reservation and coalesce into an approval round trip it must displace; a proposal awaiting approval is invalidated by Tier D rather than joined, because a proposal is not an attempt and joining one would make a trip wait for a human, and the operator's later reply to an invalidated proposal is refused and recorded rather than executed — without that refusal a YES closed the circuit the trip had just opened; a running act is never interrupted, and a Tier D arrival latches for the safety registry's retry loop rather than issuing an opposing command. A Tier D dispatch cancelled while its shielded executor is still driving leaves the command **uncertain** — neither accepted nor failed — and no opposing outcome is admitted while it stands; the uncertainty clears only when that executor finally reports. **There is no driver-call timeout**, so a driver that hangs without the dispatch being cancelled holds the resource rather than becoming uncertain, and nothing reports an uncertain command on the health surface; both are open. Two opposing Tier D outcomes on one resource are refused as an unresolved safety conflict rather than a routine refusal, because nothing acts and nothing is protected — and that classification is taken ahead of an in-flight uncertainty, since a device with two opposing Tier D outcomes is unprotected whatever the pending command is doing. **Nothing degrades safety status on it yet.** A Tier D arrival on a running opposing act is refused and the refusal recorded; the safety registry's retry loop is the owner of the displaced obligation, and **the gate is not wired to that registry**, so the latching is recorded rather than enacted. Every refusal, preemption, coalescing, invalidation and refused late reply is logged, and a bounded recent window is kept in memory for tests; **none of it is persisted to the action log**, so the durable record is the log line. The gate is consulted at the final execution boundary in the dispatcher, so an action reaching it from any caller is admitted or does not run, **and it fails closed**: where a gate is configured and an action the registry does not prove inert has no resolvable resource, it is refused rather than executed unarbitrated. Only a registry-proven informational action legitimately holds no resource. A dispatcher constructed with no gate at all arbitrates nothing, which is the pre-existing behaviour and is not reached by the runtime, where a gate is always bound. An action whose target is chosen at dispatch time — a CoAP command named by the event, a process named by a hook — resolves its resource through the same function its executor uses, registered beside it, so what is admitted is what runs. **Foreclosure belongs to the event, not to the record.** When an admitted act ends, ran, failed or uncertain, the gate records an entry under every open event that claimed it, the admitting event and each event whose request joined it in flight, at the highest tier that event put behind the act. While that event is open, an opposing request at or below that tier is refused from any event, however the resource's record is later replaced, retired or resolved, and an opposing Tier D request against a Tier D entry is an unresolved safety conflict. Only the entry's own event can join it: Tier D joins only an act that ran, a request below Tier D also joins a proposal whose operator was asked and whose executor was never entered, and a failed execution is never joined, so a later reading's trip is attempted rather than absorbed by an earlier event's act. An entry clears only when its event closes, on every exit including a cancellation, and a completion arriving after that records nothing. The scope an admission belongs to is carried per task rather than per process, so concurrent events cannot claim each other's admissions. **Cooldown has one owner.** It is charged by the plan builder when a trigger's plan is admitted, immediately before its first attempt or reasoning task is scheduled. A trigger that did not match, or whose actions were all refused at the gate, consumes nothing — the outcome is read from the dispatcher's own result after the work settles rather than assumed when it was scheduled, because an action admitted into the reasoning path can still be refused at the resource gate. Cooldown is held in memory only and a restart clears it; previously the rule engine charged a fire while evaluating and the loader charged one before the condition was known to match, so a trigger that never matched — or matched and lost — spent its cooldown. **No cooldown and no in-flight hold reads or charges against a Tier D attempt.** The rule engine never suppresses a Tier D rule, a plan granting Tier D attempts its trip on every matching reading and holds only its other actions, and the outcome a cooldown is charged on leaves the Tier D act out, so a trip that ran, failed or was refused never charges one. The rule-evaluation API reports a Tier D match on every evaluation and charges it nothing; the loader's coordinator-less handler keeps its cooldown, since that path attempts no Tier D act. A Tier D trigger whose plan grants no Tier D act is held like any other. Until the safety registry is the Tier D path, a legacy Tier D trigger has no retry of its own: its only re-attempt is the next matching reading that reaches dispatch, which the deduplicator forwards at most once per 5 s for a steady value.

## Configuration document limits

Status: Implemented. Files: config/_document.py, ori.yaml.example, tests/test_config.py.

`Config.load` answers a malformed or hostile document with a refusal rather than letting it reach the caller as an interpreter error. The document is parsed with a bounded safe loader instead of `yaml.safe_load`: it refuses nesting deeper than 32 levels, more than 20000 nodes, any mapping or sequence of more than 1000 entries, and any scalar longer than 4096 characters, and it refuses YAML anchors and aliases outright — an alias composes at its own shallow depth while referencing an already-composed node, so a chain of them builds an object graph arbitrarily deeper than the depth bound ever sees, and the recursive visitors downstream are what exhaust the stack. Numeric literal length is bounded by that scalar limit rather than left to the interpreter, whose own limit applies to decimal conversion only — a hex, octal or binary literal of any length is built without complaint — and is removed entirely by `PYTHONINTMAXSTRDIGITS=0`. A constructor failure that is not a `YAMLError`, such as an out-of-range timestamp, is re-raised with the offending node's mark so the refusal names the line. Interpretation is classified as well as parsing, because converting a parsed value refuses in its own vocabulary: `device.rated_capacity_amps` is the Tier D threshold input and is read through `float()`, where a 309-digit integer raises `OverflowError`, a string `ValueError` and a list `TypeError`; neither `runtime/_startup_foundation.py` nor `config/installer.py` catches those, so each would otherwise leave startup as a traceback and a supervisor restart loop. Both parse sites are covered: the same bytes are parsed twice, once plainly for the signature to be checked against and once with scalar-local expansion for the runtime to use, so no textually-substituted copy of the document is parsed at all. The file is read as UTF-8 explicitly rather than in the host's locale encoding, so a signed configuration decodes to the same document on every device, and a file that is not UTF-8 is refused as a bad document. Limits are stated in `ori.yaml.example`; the deepest shipped example is depth 6 with 579 nodes, 17 entries in its widest collection and a longest scalar of 54 characters. **File admission is bounded before the document is parsed.** The file is opened with `O_NOFOLLOW`, `O_NONBLOCK` and `O_CLOEXEC`, and the regular-file test is an `fstat` on that descriptor rather than a check on the path, so it holds for the file actually read. A FIFO is refused instead of blocking in `read()` — `O_NONBLOCK` is what makes that possible, since the open itself otherwise never returns — a directory or device is refused, and a symlinked configuration path is refused, matching the decision the Linux installer already makes at write time where a symlinked path or parent is an unsafe destination. `O_NOFOLLOW` covers the final component only; a symlinked parent directory is still followed. Reading stops one byte past a 1 MiB cap rather than trusting the size `fstat` reported, so an oversized document is refused without being read: the largest shipped example is 31 KB, and the 150 MB file that previously cost 54.4 s and 329 MB now refuses in under a millisecond. The cost of the worst *admitted* document is the figure to plan against, since the same bytes are parsed twice: measured across shapes at just under the cap on a 2026 laptop, 0.56 s for long comment lines and 1.01 s for a file of one-character comments, which is the slowest shape found. A Raspberry Pi is several times slower again, so a document near the cap is a startup pause rather than an instant load. Nothing shipped comes close: the largest example is 31 KB. `read_config_bytes` is shared with `ori/config/installer.py`, which admits a generated document under its own deliberately tighter 512 KiB cap. **Duplicate keys are refused.** The signature is computed over the parsed document, so keeping the last of two would mean a reviewer reading the file top to bottom sees one rated capacity while the runtime uses another, both consistent with a valid signature; non-string keys are refused with them. **Environment expansion cannot change the document's structure.** `${VAR}` is substituted into a scalar the parser has already delimited, not into the text before parsing, so a value carrying a quote and a newline stays one scalar instead of closing the quote and adding keys. A placeholder in **key** position is not expanded at all, and neither is anything inside a complex (`?`) key: expanding one would let an environment value choose a key name — `rated_capacity_${SUFFIX}` becoming `rated_capacity_amps`, or a value of `<<` becoming a merge key that rewrites the mapping — which is the same authority a textual substitution had, reached a different way. Both passes parse the same bytes, so the document the runtime builds from has, by construction, the structure the signature covered. Typing is unchanged: an unquoted scalar takes implicit typing from the substituted text and has its surrounding whitespace stripped as the parser would have stripped it, a quoted one stays a string, and an explicitly tagged one keeps its tag. One difference is deliberate: a `#` in a substituted value no longer truncates the scalar as a comment, because honouring it would be letting the value alter the document again. Expansion is the same in every deployment, signed or not: there is one loader. `read_config_document` is shared with the other readers of `ori.yaml` — `installer/paths.py`, `installer/identity.py` and `phone_doctor.py` — which each parsed independently and caught only `yaml.YAMLError`, so a bound added here applies to every reader of the file.

## Sensor configuration schema enforcement

Each adapter module exposes `refuse_unusable_config(config)`, the checks its
`connect()` makes from the configuration alone: supported sensor types, blank
required strings, an inverter profile and its metrics, Zigbee and LoRaWAN value
paths, the CoAP URI and its host in the sensor's `allowed_hosts`, and the
ADS1115 calibration. `connect()` runs it, and config load runs it on the
mapping `connect()` would receive (`connect_config` in
`hal/protocol_registry.py`), so the two cannot disagree. The registry resolves
it without constructing an adapter, and a protocol whose module lacks one is
refused at load. A non-finite number is refused in every field, and a network
or serial timeout below 1 ms (`MIN_TIMEOUT_S`) in every spelling.

The checks read the configuration and the bundled inverter profiles and
nothing else: a missing driver, missing hardware and an unreachable endpoint
stay connect-time failures. Sensor types are checked here rather than by
`parse_sensors`, the `sensor-configuration/v1` boundary, which leaves the
vocabulary to the adapter that consumes it.

## Measurement supervision and withheld-measurement posture

Status: Partial. Files: hal/ac_measurement.py, hal/i2c_adapter.py, safety/registry.py, runtime/_measurement.py, runtime/_measurement_policy.py, runtime/_sensors.py, docs/MEASUREMENT_SUPERVISION.md.

A window that cannot be shown to be a measurement is refused rather than published, so a safety condition defined over that channel is not evaluated against a plausible number. A current window whose mean sits outside the bias midpoint's derived tolerance is refused, which catches a disconnected input; a clamp uncoupled from its conductor holds the midpoint and reads as an idle circuit, is not detected, and commissioning catches it only where the circuit leg records the bound sensor's readings, which the contract permits and does not require. Three consecutive refusals mark the sensor degraded and five consecutive good windows clear it, recovery being deliberately slower than failure because a path that alternates is not trustworthy. A chip found running a configuration this runtime did not set during a measurement is quarantined by `(bus, address)` for the life of the process, since clearing it needs the competing writer gone and no reading can establish that. Health reports the degradation per sensor, with the latest refusal's reason, and in the aggregate `status`, and a Tier A notice fires on the transition and then at six hours, twelve hours and daily, escalating to the secondary contact, with no give-up: a still-unprotected channel must not become permanently silent. **A device reporting a withheld measurement is not protecting that channel, and escalation does not restore protection — it tells a person the channel is unprotected.** The same mismatch found at `connect()` quarantines the chip too, though it is the weaker evidence of a competing writer rather than the stronger: the connect readback is also what identifies the part, so it cannot separate a contested chip from one that is not an ADS1115, while a measurement-time mismatch has both excluded by a successful connect. Latching on it is still correct because every reading of the fault justifies refusing the chip, and without it the released bus claim let a second adapter — reachable because `ori.yaml` checks sensor ids for uniqueness and not addresses — configure a chip the first had just refused. A readback that could not be performed at all latches nothing, at connect as during a measurement, because a bus failure is evidence of nothing. **Partial**: pair-scoped supervision is implemented and dormant — `watch_measurement_loss` degrades a pair, alerts and holds trip state, and the pair-scoped health view exists — but it binds to nothing while every shipped profile is a `candidate`, and it emits neither the sensor responsible nor a duration, while the evidence half is undesigned and nothing under `security/evidence/` refers to measurement at all — those gaps are #565. A timed self-restart and watchdog-health coupling are both refused with reasons recorded, and the five prerequisites any reset-based response would need are written down with none met.

## Tier C approval workflow

Status: Implemented. Files: action_dispatcher.py, tier_c_admission.py, approval_bounds.py, state/_tier_c.py, runtime/_startup_foundation.py, runtime/_commissioning.py, tests/test_tier_c_governed_approval.py, tests/test_tier_c_approval_sequences.py.

A physical Tier C action on a commissioned zone is proposed and admitted under `tier-c-approval/v1`: the proposal row is committed before the operator is asked and binds the zone, the binding digest and a closed authority snapshot; an affirmative reply is an approval only inside one store transaction that byte-matches binding and authority, checks the same-outcome block, reserves the terminal record and claims any token; dispatch follows immediately with nothing written ahead of the executor; the outcome is appended after and retried while live; a restart records `dispatch_not_proven` or `dispatch_outcome_unknown` and never replays; a graceful stop closes open proposals; an uncertain dispatch blocks only its outcome on its zone until reconciled by an authenticated operator record or commissioned feedback, by `evidence reconcile-tier-c` over the operator socket, or by commissioned feedback. Expiry is on the process's monotonic clock; `approval_timeout_seconds` is bounded at load to 1..release maximum. A physical Tier C action with no zone, and `coap_command` at Tier C, are refused as proposals. Host-state Tier C actions and Tier B actions requiring approval use the existing workflow: the request includes a short `proposal_id`, scoped `YES-<id>`/`NO-<id>` replies must match by default, and bare remote `YES`/`NO` is legacy/test opt-in only. The contract's admission sequences are replayed through the real dispatcher against a real SQLite file; what this runtime cannot represent is stated per step (no affirmative non-dispatch record, so `approval_aborted_undispatched` is unreachable; alert retry belongs to the outbox).

## Gateway/reporting data exports

Status: Implemented. Files: state/_history.py, state/_actions.py, state/_tier_c.py, state/_reasoning.py, gateway/export.py, runtime/_services.py, runtime/_health.py.

Runtime exposes provider-neutral bounded exports for action logs, Tier C decision logs, reasoning logs, sensor history, and health. Gateway/provisioning services request data over MQTT (`ori/{device_id}/export/request` → `ori/{device_id}/export/response/{request_id}`) without direct SQLite table knowledge or runtime cloud SDK dependencies. Authenticated deployments verify export requests and sign export responses with HMAC envelopes. Sensitive export responses can be AES-GCM encrypted above the broker layer so sensor/audit rows are not visible as plaintext MQTT payloads. Sensor-history responses support `bucket_ms` aggregation and pagination for weekly reports. Reasoning-log export includes `reasoning_status` and `correlation_id` for reliable action/reasoning joins.

## Runtime HTTP telemetry export

Status: Implemented. Files: telemetry/http_export.py, runtime/_services.py, runtime/_startup.py, config/_telemetry_export.py.

Optional direct provisioned telemetry export for phone/lightweight deployments. The runtime mirrors the readings it publishes — canonical `sensor.reading` events and typed `sensor.<sensor_type>` events — to a bounded async queue, written into each batch as `sensor.reading`, and POSTs HMAC-signed batches to a configured HTTPS endpoint. This path is disabled by default, does not replace gateway MQTT exports, and never participates in Tier B/C/D action authority. A batch counts as delivered only when the receiver's answer accounts for every event in it, read under strict, bounded body parsing shared with the Android payload through one vector set. Unconfirmed batches are retained in memory within the bounded queue; one the receiver answers five times without confirming is discarded and counted as `unconfirmed_events`, and a recorded terminal refusal suspends export alone. Durable backfill remains a future provisioning-sync concern.

## Android runtime mobile payload

Native runtime for the phone lab and contingency profile; a phone is not a deployment shape. ## Signed Android payload publication

Status: Implemented. Files: ori/security/android_payloads.py, scripts/sign-android-runtime-payload-aws-kms.py, scripts/verify-android-runtime-payload.py, scripts/verify_published_release.py, scripts/check-android-payload-build.py, ori/installer/android-payload-keys.json, .github/workflows/release.yml, .github/workflows/android-payload.yml, tests/test_android_payload_publication.py.

Implements `runtime-mobile/v2`, with the producer and the reference verifier both driven by the vendored conformance corpus: every case reaches its recorded stage and reason, every registry case loads or is refused as recorded, and a registry holding any key whose seed this repository publishes is refused at load through the shared `published_test_keys` set, and the producer reproduces each accepted envelope byte for byte. The corpus cannot reach the two producer gates that read the build itself, since its images carry no Android note, so the API-level and strip-state checks are held to synthetic images and to real built payloads instead. The release workflow builds the three payloads from the tagged commit with a pinned Rust toolchain, `cargo-ndk` and NDK in a job holding no signing authority; the single `sign` job signs the complete target set through the release KMS key under the `android_runtime_payload` purpose, measuring the strip state and checking the recorded API level from each ELF image, and writes no envelope unless every target signed and verified; `publish` verifies every payload before the draft exists, and `reverify` verifies them again from the public release origin. The same build steps run on every pull request that can affect them. Digests reproduce across source directories, target directories, Cargo homes and `rust-src` installation state on one host, because the build remaps the Cargo registry and the toolchain sysroot out of the binary and refuses a payload carrying any path under the builder's home, and every release rebuilds each payload from a fresh copy of the tagged commit and fails if a digest does not reproduce. Across host operating systems the digests differ, measured between macOS arm64 and the Ubuntu runner image: the difference is confined to `.text` and the unwind tables, where the NDK's host-specific prebuilt runtime libraries land, while every section built from the crate's own data matches. A payload's digest identifies what a release published on its runner image; it is not a value another host reproduces. `v2.5.0-rc.10` published the first three payloads and every job ran: signed through the release key under the `android_runtime_payload` purpose, verified before the draft existed, and reverified from the public origin after publication. Each published payload was then fetched by tag and verified independently against the shipped registry, records API 21 and `stripped`, and is refused when offered for another ABI slot; the published arm64 digest equals the one the pull-request runner built, so the two images of that operating system agree. The consuming application's verification is that application's to implement.

## Inverter profile registry

Status: Implemented. Files: hal/inverter_profiles/, solarman_modbus_adapter.py, protocol_registry.py, tests/test_inverter_profile_qualification.py.

Runtime-wide capability for phone, Pi, Linux/server, and Ori Edge Node deployments. Ori can load bundled inverter register profiles as data, validate qualification status, enforce golden decode vectors, and read SolarmanV5 profiles through a generic read-only `solarman_modbus` HAL adapter. The registry supports numeric metrics plus enum lookup and string-register decode for offline qualification/tooling; live `SensorReading` values remain numeric-only and the Solarman adapter rejects non-numeric metrics. Bundled `growatt_spf` and `deye_hybrid` profiles are `community_derived`, not `field_qualified`; Deye/Sunsynk/Sol-Ark remain Deye-family qualification candidates until field evidence is captured for exact model/firmware/logger combinations. ## Inverter profile doctor

Status: Implemented. Files: inverter_profile_doctor.py, tests/test_inverter_profile_doctor.py.

Offline CLI for listing bundled inverter profiles, validating golden decode vectors, decoding raw register samples, generating fill-in evidence templates, and reviewing local field-evidence JSON bundles through the same registry decoder used by the runtime. Evidence review checks brand/model/firmware/logger identity, transport proof, operating state, timestamped LCD/app proof references, optional PZEM/clamp comparison references, samples for every metric in the profile, and decoded-vs-observed tolerances. ## Prosumer energy ledger

Status: Implemented. Files: policy/prosumer_ledger.py, skills/prosumer-energy-advisor/, tests/test_prosumer_ledger.py, tests/test_prosumer_energy_advisor_skill.py.

Device-side fast-loop ledger for operational estimates plus a validated monthly DisCo settlement-statement shape. The fast-loop ledger accumulates bounded kWh/value deltas for grid import/export, solar generation, site consumption, optional battery charge/discharge, generator use, backup-supply hours, explicit grid-unavailable hours, exported value, self-consumption value, and diesel-displacement estimates using skill-isolated state. ## Prosumer energy advisor

Status: Implemented. Files: skills/prosumer-energy-advisor/, tests/test_prosumer_energy_advisor_skill.py.

Tier A bundled skill that turns normalized PV, grid, load, battery, and generator telemetry into deterministic consume/store/export/defer/preserve-reserve/reduce-generator advisories. The skill treats tariff/export-credit, export-cap, and generator-cost values as operator-provided policy inputs, distinguishes operational estimates from DisCo billing truth in config comments, and only dispatches informational alerts/logs. Export-cap policy is deterministic: the skill computes cap headroom, exportable surplus, local-use/store surplus, warning threshold, and exceeded state; it never recommends adding grid export when the configured cap blocks it. The advisory optimizer estimates naira-per-hour value for self-consumption, export, deferred load, and generator reduction without writing inverter/generator registers, changing export limits, or introducing Tier B/C control.

## Phone install doctor

Status: Implemented. Files: phone_doctor.py, scripts/phone-doctor.sh, docs/android-phone-install.md.

`ori-phone-doctor --config ori.yaml` validates Android/Termux readiness for the phone lab profile without starting the runtime loop. Checks include Termux command availability, wake-lock helper presence, USB readiness, `deployment_type=phone`, relay disablement, gateway posture, signed-config posture, USB/Growatt/SolarmanModbus/Victron sensor profile config, profile dependency availability, telemetry API-key environment state, Termux-writable health socket posture, and operator contact placeholders. The USB-dependent checks — `usb.readiness` and `command.termux-usb` — are decided together from the loaded configuration and are omitted entirely when no sensor declares the `usb` profile, so a LAN-inverter deployment is no longer told that USB hardware it does not use is missing. They are retained when the configuration cannot be read, since the profile is then unknowable and omitting them would hide a real USB problem at exactly that moment. Checks are omitted rather than reported under a new status, because `_STATUSES` is a closed set that at least one downstream consumer already maps onto an operator-visible health state. `termux-usb -l` output is parsed by `ori/utils/termux.py:parse_termux_usb_output`, shared with `usb_serial_adapter.py`: the command exits zero while printing prose, and every non-device line was previously returned as a device path, so the doctor reported that termux-usb saw devices for output saying the opposite and the adapter raised a connection error naming a USB-serial bridge instead of the missing `device_path`. Only entries that name a device path are returned now.

## Production security posture enforcement

Status: Implemented. Files: config/_posture.py, runtime/_startup_foundation.py, runtime/_gateway_wiring.py, ori.yaml.example, AGENTS.md.

`device.deployment_profile` set to `staging` or `production`, or `security.enforce_production_posture: true`, fails config load for unsafe production settings. Staging/production profiles cannot opt out with `enforce_production_posture: false`. ## Runtime config signature verification

Status: Implemented. Files: security/config_signatures.py, config/_config.py, ori.yaml.example.

Runtime verifies backend-generated `ori.yaml` files with an Ed25519 `config_signature` envelope before trusting the parsed config. The signed payload covers the unexpanded YAML body plus signature metadata. Environment interpolation still happens after verification, but it can no longer change what was signed: `${VAR}` is substituted into an already-delimited scalar rather than into the document text, and never into a key, so a variable the document merely names cannot add, remove or replace a key. Before that, a value carrying a quote and a newline could rewrite any key in a verified document, and a placeholder in key position could name one, `device.rated_capacity_amps` in both cases. The trust anchor is intentionally supplied outside the YAML through `ORI_CONFIG_TRUST_ANCHOR_PUBLIC_KEY_B64` or a configured env name, so a tampered config cannot swap its own public key. Private APK / production launchers can force fail-closed verification with `ORI_CONFIG_REQUIRE_SIGNED=true`; production posture also requires a verified config once all other hardening checks pass. Because the signature covers the document before expansion, a `.env` loaded through `ORI_AUTOLOAD_DOTENV` supplies the value of a signed field without invalidating the signature. Staging and production refuse the autoload outright — before the document is read, from the posture declared in the unexpanded YAML, and again once the parsed document declares it — and a development deployment that carries a signature keeps running and reports it: health carries `config_authority`, whose `unsigned_value_source` says a signature was asked for and a file outside what it covers supplied a value the document expands. Both halves are measured rather than assumed: `load_dotenv` runs with `override=False`, so the autoload reports the variable names it actually introduced rather than that a file existed, and `config_env_placeholders` reads which variables the unexpanded document's values name, so a `.env` naming none of them decides nothing and is not reported. Unknown is not none — a document that could not be read leaves a loaded file assumed to have decided something. The health payload's `status` and the node heartbeat derived from it read `degraded` while that holds; `ori doctor` reports on the service unit and does not read this field.

The profile's status is carried onto the active pair at activation and re-checked where the claim is made, so a regression in the activation checks can no longer produce a false `protected`; the pair's activation is read from the registry's own active set rather than taken as a string from the caller, and a caller naming a pair that is neither active nor carrying a verdict is refused rather than given a token `runtime-health/v2` does not define. That is short of every conjunct standing alone: drivability is a constant `False` until #482, and the status re-read is written only by the activation branch the earlier check gates. Only `active` pairs count: a pair held for ratification or refused reports `unprotected` correctly, the device never undertook to protect it, and degrading on those would leave every device carrying a candidate profile permanently degraded. It degrades and never raises `critical`, and it changes nothing about Tier D — the protection path neither reads the health snapshot nor is gated by it. The consequence to expect is fleet-wide: because drivability is a constant `False` until #482, the first ratified profile makes every device carrying one permanently degraded on a fully commissioned zone with nothing else wrong, and `degradation_reasons` carries no token that can say why (ori-platform/ori-specs#171). Because every shipped profile is a candidate, no deployed pair gains protection from any of this.

## Outbound alert outbox + retry

Status: Implemented, host-tested. Files: actions/alert_delivery.py, actions/alert_failover.py, runtime/_alerts.py, runtime/_startup_foundation.py, state/_alerts.py, config/_actions.py.

Store-and-retry queue retains the typed alert intent and bounded template variables across restarts and channel failover. Provider acceptance is recorded separately from handset delivery; only a later provider receipt supplies `delivered_at_ms`, and legacy rows that called submission success `delivered` migrate to `accepted` without inventing a handset fact. Retry interval, batch size, non-Tier-D attempt limit, and Tier D critical warning threshold are configurable under `actions.alert_outbox`. Runtime health snapshots expose backlog count and oldest queued alert age. Each row stores its `notice_kind`, decided once when the notice is created: `tier_d` only for the notice of a first-party skill's matched Tier D trigger, `protection_degraded` for the runtime's own protection notices, `optional` for the rest. A mandatory notice passes no customer preference or monthly cap, is not counted against the cap, and is never abandoned; the store itself abandons only `optional` rows, so an unknown stored value is kept. The notice stays a Tier A act: `alert_whatsapp` and `alert_sms` record Tier A whatever tier a skill declares for them, so a declared tier grants no cap or preference exemption. Retries are first in, first out by a store-side queue position, never the clock: a row takes the next position when queued and again after each failed attempt, so no later row overtakes it. Each batch draws from two lanes, mandatory and optional, each given at least half the batch rounded down with an odd batch's spare slot alternating, and room one lane leaves goes to the other, so sustained traffic in one lane cannot keep the other's rows waiting. Delivery receipts are polled in the same queue order: an accepted message takes the next position when accepted and again after each poll that settles nothing, so messages a provider never reports on cannot keep newer ones from being polled. Each awaiting message is polled within ⌈N/batch⌉ passes, where N, the messages awaiting a receipt, has no bound: a transport that reports no receipts, or a provider that never answers, keeps its messages awaiting for good. Neither acceptance nor polling proves handset delivery. The monthly cap is a budget limit, not an exact billing guarantee. It counts each observed provider acceptance of an optional notice, with one atomic increment on the accepting channel, never a refusal, and records usage under an unlimited cap too. It is judged at enqueue, after the preference and before the recipient, and again before every optional provider call: first sends, retries and each failover destination, so an optional notice never reaches a channel whose cap is spent. The cap governs the outbox's notices only: Tier C approval requests, proposal-outcome notices, the secondary-contact escalation and the emergency SMS for a failed Tier D action are workflow and safety communications it neither counts nor checks. A queued notice with no channel under its cap waits behind other work, charged no attempt and never abandoned, until budget returns; that keeps the obligation but bounds neither the queue nor how late it is delivered. Optional submissions authorised concurrently, before any of them is counted, can exceed the cap; a lost provider response or a failed count write undercounts, logged at ERROR. An optional notice the cap withholds at enqueue is tallied `capped` beside the `disabled` tally of a preference, one count per channel, class and month of the runtime's clock.

## Ed25519 community skill verification

Status: Implemented. Files: skills/_loader.py, skills/_core.py, skills/_provenance.py, skills/signing.py, tests/test_skill_signing.py.

Community skill manifests require a valid `ed25519:<base64>` signature over strict canonical JSON against the Hub manifest trust anchor; duplicate YAML keys, non-string mapping keys, non-JSON values, cycles, and non-finite numbers fail closed. The canonical-manifest profile is pinned to the shared `ori-specs/signing/v2.md` vector digest. Trust anchors resolve in safe precedence (`SkillLoader` override → `ORI_HUB_ROOT_PUBLIC_KEY_B64` env → fail-closed sentinel). As of v2.4.0 every skill that does not ship with the runtime must carry a verified Ed25519 manifest signature, regardless of `security.skills.require_signed` — that setting previously exempted skills outside `~/.ori/skills` from verification altogether, which included the operator-managed directory beside `ori.yaml`. Provenance is now positive: first-party means packaged with the runtime (source checkout or installed wheel), and those may still use `signature: bundled`. `require_signed: true` additionally requires packaged skills to carry a recognised declaration prefix (`bundled` or `ed25519:`); the value is not decoded or verified — a packaged skill's authenticity derives from the signed release artifact it was installed from, not from the manifest declaration. A trust anchor naming a key whose private seed this repository publishes is refused in `verify_signed_payload`, which is the shared verifier for community skills, offline Tier C approval tokens and device policy, so one check covers all three rather than each call site being remembered separately. The skill loader refuses the same material again at admission, where it can name the source a deployment actually configured — the constructor override or the environment variable — which the shared verifier cannot know; each layer fails closed on its own. Every way an anchor can authenticate nothing is decided there — unconfigured, empty, not base64, non-canonical base64, the wrong length, or a published seed — because the same answer decides both whether to refuse the skill being read and whether the deployment can admit any community skill at all, and leaving the malformed cases to the verifier answered only the first: it refuses per skill, in a vocabulary no report reads, so a device whose anchor decoded to nothing refused every community skill while reporting the anchor usable. One fault still yields one message, because this refuses before the verifier is reached. Neither the gateway nor the Skills Hub has run in a production deployment (#545). An anchor that cannot verify anything is a property of the deployment, not of the skill being read when it is noticed, so it is answered once before any skill directory is opened and reported as one fact: the refusal is a `SkillAnchorError`, `load_all` logs a single line naming the affected directories rather than one line per skill, `skills list` publishes `community_anchor` and classifies those refusals as `community_anchor_error`, and health carries `community_skills` with the anchor's usability and the number of community skills the load did not admit. Reporting and attribution are separate questions: an anchor that is a well-formed key but not the Hub's refuses every community skill with a signature failure that cannot be told apart from a tampered manifest, so it is not attributed — but the device still knows the skills did not load, and the count carries that whether or not the fault can be named. What degrades a device is that count, never the anchor: the anchor a build ships with is unconfigured, so degrading on it would report every device running only first-party skills as unhealthy for a capability it is not using. A packaged skill that fails to load is a fault in the release rather than in community admission and is not counted. Detached exact-artifact verification before extraction belongs to the SDK/CLI/Skills Hub install path and is not a runtime-loader responsibility.

## Commissioned safety binding

Status: Partial. Files: security/commissioning/binding.py, security/commissioning/anchors.py, security/commissioning/loader.py, security/commissioning/profiles.py, security/commissioning/profiles.json, state/_commissioning.py, runtime/_commissioning.py, runtime/_startup_foundation.py, config/_actions.py, docs/COMMISSIONING.md.

Implements the consumer half of `ori-specs/commissioned-safety-binding/v2`: the binding envelope at `commissioning/binding.json` beside `ori.yaml` is verified through the contract's twelve ordered stages against the commissioning anchors the installer delivers in the service environment, the accepted binding, the inventory the provisioning document declares, the deployment posture and the release-shipped safety profile set (`safety-profile/v1` `profiles.json`, vendored byte-for-byte and loaded under its closed grammar); every verdict names its stage and reason; an accepted binding is retained whole in the state store with its predecessors retired, never deleted; `anchor_collision` refuses every start at configuration load; declared actuating hardware with no binding in force refuses a hardened start and degrades a development one; health reports the retained zones, provisional or in force, and the last verdict. The runtime's verifier is driven over the vendored golden corpus (21 accept at their declared states, 120 reject at their declared stages, 13 firmware-profile, 11 envelope and 7 raw cases). A trust anchor whose private key this repository publishes is refused wherever one is read — both commissioning slots, the configuration-signature trust anchor, and the provisioning anchor — at every deployment profile, because a development runtime drives the same relay as a production one. The refused set covers every seed discoverable in tracked files plus trivially guessable ones, is append-only because a seed rotated out of the tree stays in history, and is re-derived by test so a newly committed seed cannot escape it. A device carrying such an anchor refuses to start rather than starting on a forgeable authority (`GHSA-rv38-92xc-7xq8`, fixed in `v2.5.0-rc.8`). The proof carries two legs: `proof` establishes the circuit, and the optional `proof.control_path` establishes that the pin the binding names, at its declared `active_high`, is what moves that coil. Absence of the control leg denies rather than grants, so a document passing every stage with either leg unproven on any zone is **provisional**: retained in `commissioned_binding_provisional`, reported, outside the freshness chain, and never connected or commanded — the initialisation coil command included, because that command is itself derived from the polarity under test. `commanded_and_observed` is admissible only for `local_gpio`, so a `firmware_channel` zone is always provisional. The in-force table refuses a provisional document at the write, and the loader migrates a retained row whose legs are not both proven into the provisional record before retiring it, so the device keeps a per-zone unavailable report. The revision rule applies leg by leg: a change to any field of a zone's sensor, its actuator identity or its mapping requires every leg the revision claims to be performed after the same leg's retained time, whichever field changed, while an unclaimed leg is held to no time and leaves the zone provisional, so a revision cannot inherit a control proof taken at the polarity it replaces. `actions.relay.active_high` is refused from `ori.yaml` as a foreign field. The commissioned actuation seam (`actions/commissioned_actuator.py`) is the only path to the relay: the pin is connected under the zone's polarity, startup commands the coil `de_energised` through it, `trip_relay` / `close_gas_valve` / `release_relay` resolve to protected-circuit outcomes through the zone's mapping at the moment of actuation, a declared pin with no zone in force is not driven and registers no relay action, every logged physical action carries `binding_seq`, and health reports the actuator's coil and last command. The commissioning proof operation (`security/commissioning/proof_operation.py`) closes the control leg: runtime-owned code a local tool invokes and does not perform, issuing exactly one consented coil command against one provisional zone. It refuses by name for no provisional binding, a zone already in force, hardened posture, a non-`local_gpio` zone, an unknown outcome, or an absent GPIO backend, and has no simulated path. Consent is taken from `/dev/tty`, which the operation opens itself with `O_NOCTTY` on both handles so it uses the terminal the operator already holds and never acquires one; it cannot arrive as a bridge argument, a flag, or piped stdin, one authorisation permits one command, and consent and actuation are a single audit row. What that establishes is that a process holding the controlling terminal answered: the nonce is printed to the same terminal it is read from, so a parent that allocates a pty can supply it, and no POSIX check distinguishes that from a person. A terminal is therefore not treated as proof of physical presence and is not reported as such; presence remains a commissioning procedure requirement. Taking a GPIO line as an output drives it: gpiozero offers no high-impedance output, and `initial_value=None` only declines to choose a state, leaving the register's value — measured on a Pi 4 with gpiozero 2.0.1 at `active_high=False`, `None` drives the line low, which on an active-low stage is *energised*, where `False` drives it high. The line is taken *at* the requested coil state, so one authorisation produces one output-state command: a path that took the pin at de-energised and then commanded the outcome issued two physical acts for one consent, briefly putting the zone in its de-energised terminal state -- whatever commissioning recorded that to be -- rather than the outcome authorised. Nothing follows the acquisition -- no trigger, no release -- and the consent prompt says so before the operator authorises. Acquiring at a chosen coil state is not a general relay capability: `RelayAction.connect` takes the line de-energised and accepts no coil state, `acquire_at` is the only way to take one already energised, and the commissioned seam is its only caller. Ordinary runtime startup keeps its explicit `command_coil("de_energised")` path, which is a different guarantee. The commanded level is held while the operator answers -- at least a release-owned one second however fast they are, and at most sixty, neither configurable from `ori.yaml`, a flag or the environment. The hold and the answer window are the same interval because the facts being attested are only true while the command is in force; a five-second fixed dwell was long enough for the read itself but not for a person to read a prompt, look at a panel and answer twice, so on the bench every attempt timed out and each timeout cost another actuation. The operator is asked on the same terminal for the contract's own observation fields: `load_present_before` before consent, then `terminal_state_observed` and `load_present_after` during the dwell. The verdict is derived from those facts, never taken as a separate answer that could contradict them, and it uses the same load-transition rule the verifier applies, so a command whose load never changed state is `inconclusive` rather than a proof. Input typed before the coil moved is flushed, because an answer already buffered describes an effect that had not happened. Sensor readings and the instrument are carried by the observation but never populated here: this command asks for no measurement, so a leg needing a reading obtains it another way. Silence, cancellation or an error records `observation_timeout` and produces no proof; a terminating signal is turned into a cancellation so the release still runs. The runtime never observes the coil, so `effect_verified` is always false and no parameter exists to set it; the response reports `command_issued`, `effect_verified`, `operator_attestation` and `release_requested` rather than a single `executed`. It is released to an undriven input on every exit **where the operation's own code runs** -- refusal, driver error and cancellation included -- and never parked in a chosen state on the way out. That release is not the zone's controller-loss condition, and on the bench Pi 4 the two modes were measured to differ: loss of power de-energises the coil, while a process killed outright leaves the pad driving and the coil commanded, because releasing a line needs code to run. No software release covers that mode, so a zone whose hazardous state is the energised one needs a hardware fail-safe that removes coil power -- itself safe only where commissioning established that the resulting terminal state is acceptable. `commissioning proof-export` is read-only and accepts no observation, consent, pin value or claimed outcome. `commissioning binding-export` is read-only and returns the envelope in force, rebuilt from the retained canonical bytes and signature and refused when they do not reproduce the recorded hash, so a revision starts from the document the device holds; it never exports a provisional binding, creates no state store, and opens an existing one read-only, changing no byte of it and creating no file beside it. A revision needing fresh legs on an actuator the binding in force still binds cannot yet be proven: the proof operation refuses that actuator, and taking a zone out of operation to prove it is not yet specified. **Partial**: profile activation, arming, latched trip state and the migration of the packaged Tier D triggers to outcomes are #324; a circuit leg authored through the operator CLI has not yet brought a zone into force on hardware. The seam's behaviour on real hardware is recorded in `docs/evidence/2026-09-22-pi4-circuit-leg-proof.md`, where a bench zone with both legs proven came into force and the seam connected the relay and commanded the coil de-energised at start. The ceremony through the operator CLI is recorded in `docs/evidence/2026-09-23-pi4-revision-ceremony.md`: a revision exported, captured, signed and delivered without `--force` came into force; a fresh-leg change on a driven line and a stale revision were refused; and a first commissioning reached a provisional binding carrying a control leg proven through the CLI and exported from the runtime's record.

## State history compaction skew guard

Status: Implemented. Files: state/_history.py, runtime/_loops.py, config/_state.py, ori.yaml.example.

Compaction enforces explicit cutoff ordering and never halts on a receipt dated beyond the clock by more than `state.compaction.max_backward_skew_ms` (default 1h), since a clock behind only moves the cutoffs earlier. Nothing is deleted for such a receipt, in any tier: the kernel's synchronized flag is not an authenticated time, so a source that stepped the clock back while reporting synchronized would turn a prune into the loss of an incident's raw trace. On a device whose clock ran ahead the rows therefore persist until the clock passes them, which is bounded storage growth. Age windows (`avg_last_hours` across every tier, the latest-readings snapshot) leave out any receipt more than a minute after now, since its age is unknown; the minute covers the store stamping a row just after its event and a small backward clock step. A receipt between the minute and the skew bound drops out of those windows without a log line. Arrival-order reads (`get_history`, `avg_last_n`) still include it. Future receipts are logged when their count changes and daily, not every cycle. A receipt is the store's clock at insert, so it is not refused there; marking a clock discontinuity at insert, and recovering storage on a trusted time, are not implemented. The energy-anomaly-detector's observed window excludes receipts more than a minute after the event's own and never exceeds raw retention.

## Evaluation-time history

Status: Implemented. Files: network/events.py, state/_history.py, runtime/_sensors.py, runtime/_startup_foundation.py, runtime/_remote_commands.py, gateway/firmware_telemetry.py, reasoning/rule_engine.py, reasoning/elevator.py, gateway/reasoning.py, skills/hooks_api.py, skills/os_sandbox.py, skills/energy-anomaly-detector/hooks.py, tests/test_history_frontier.py.

A reading is never part of its own history. When a reading is admitted, the store stamps the event with its history frontier, the last `sensor_history` row it had committed, and only then queues the reading's own row; ids are assigned in commit order, so the bound is insertion identity, never a value, a producer timestamp or a receipt time. Every evaluation-time view reads rows at or below that frontier: rule-condition history, tier selection and its battery read, prompt placeholders, hook history, the cross-sensor context snapshot, the Tier C decision record's history window and the gateway reasoning context. A Tier D threshold change is refused while any evaluated reading is still unstored, because it checks the latest stored reading for an active condition. A row committed after the frontier, the reading's own included, is excluded even once it has landed. The same-weekday baseline reads hourly aggregates only, which never hold a row young enough to pass a frontier. Administrative and export reads of persisted history take no frontier and are unchanged. Local readings no longer wait for history or recovery persistence: the history row is queued beside the reading, and a sensor completing its recovery run is published at once while the clear is queued, one per sensor, the sensor staying degraded in memory until the clear lands; the clear and any restore go through one ordered writer that retries a locked store and counts any other failure lost. A clear that is lost is queued again on the next valid window. A refused window arriving while the clear is written leaves the disk saying recovered while the sensor is degraded; the sensor is then owed a restore of its degraded row, retried on every later window until the disk agrees, each failure counted. A run that completes while that restore is in flight waits for it and then queues a fresh clear; one that completes after a restore was lost finds the disk already recovered and needs no second clear. At shutdown the writer closes before the store: a write in flight past its grace is counted unknown, since the store may still take it, and one never started is counted lost, leaving that sensor's row degraded on restart. Firmware history persistence is off the reading's path too. Admission is bounded; a row past the ceiling, refused by the store, or not taken before shutdown is counted lost and logged with its sensor, timestamp and event, one warning per row. The safety registry observes a locally polled reading before its row is admitted. Firmware freshness verification stays ahead of publication, because it is the check that the telemetry is live and not replayed: evaluating first would act on a reading the runtime has not yet established is current. That check advances a durable high-water mark, so firmware freshness admission remains fail-closed and can still wait for the store's busy timeout, and a failed write refuses the reading. This is a deliberate replay-safety boundary, not full satisfaction of the locked-store claim; moving it off the store needs a restart and replay model first. The energy-anomaly-detector's spike ratio and pc-system-health's disk write rate compare the reading with the one before it; each compared the reading with itself while its own row was in its history. The energy detector's volatility, sustained-overdraw and observed-window spans count this reading explicitly, so their sizes are unchanged.

## Operator socket (Tier C reconciliation, commissioning reference, approver registry)

Status: Partial (runtime and bridge implemented and host-tested; deployed admission remains partial because the installer does not write `operator-uid`). Files: operator_socket.py, runtime/_services.py, runtime/_commissioning.py, cli_bridge.py, state/_tier_c.py, state/_commissioning.py, security/approvers/requests.py, tests/test_operator_socket.py, tests/test_operator_socket_reconcile_vectors.py, tests/test_evidence_commission.py.

`operator-socket/v3`: every request is one JSON object and one LF, at most 16,384 bytes counted as they arrive and refused `payload_too_large` before anything is parsed; a request with no LF by the read deadline or the connection's end is `invalid_arguments`, as are a member named twice outside a revocation document, nesting past 32 levels and a string with no UTF-8 form. The runtime binds `operator.sock` in the runtime directory systemd provides (`RUNTIME_DIRECTORY`), granting no group or world access; when an operator identity is installed it grants that user ID connect on the socket and search on the directory, and on any ancestor it cannot otherwise search, by access-control entries naming it. A socket it cannot bind or grant is logged at CRITICAL with its path and the error, and none is left behind; with no runtime directory it binds nothing and says so. The caller is established from kernel peer credentials alone (`SO_PEERCRED`; the audit login user ID only for a peer pinned by `SO_PEERPIDFD`); root and the installed operator identity, read from `operator-uid` at the install root only when the file, the root and every ancestor are root-owned and writable by no one else, are admitted. One JSON request whose members are closed per operation: seven for `reconcile_tier_c`, and `operation`, `reference` and `force` for `evidence_commission`; refusals in the contract's order, then `runtime_store_unavailable`, `state_store_locked` and `cancelled`. `evidence_commission` is recorded through the runtime's own store writer against its own device and current anchor epoch in one `BEGIN IMMEDIATE` transaction, durably before success; a registration that cannot be read is `runtime_store_unavailable`, not `evidence_epoch_unavailable`. `evidence reconcile-tier-c` and `evidence commission` in the bridge refuse bad arguments (and a malformed reference) before they connect, verify the socket peer as the runtime service identity of its installation before sending, read no configuration or health snapshot, never open the store, and relay the runtime's answer, a success only when it answers the request submitted (the reference, or the proposal, device and zone); the socket is the only path by which a commissioning reference is recorded. The contract's reconcile corpus runs through the real socket and bridge; commissioning is driven through the real socket and bridge entry point under an audit hook that records any store, file or socket the bridge touches. The installer does not yet write `operator-uid`, so an installed runtime admits root alone; a user-scope install cannot admit an operator identity under the contract's ownership rules. Without `RUNTIME_DIRECTORY`, which only the service unit provides, nothing is bound: a WARNING in development, CRITICAL in staging and production.

## Health/status RPC socket

Status: Implemented. Files: runtime_health_socket.py, runtime/_services.py, runtime/_health.py, config/_health_socket.py, tests/test_runtime_health_socket.py.

Read-only Unix domain socket RPC (`/run/ori/health.sock` default) returns capability posture, sensor status, last alert timestamps, DevicePolicy state, advisory remote-command lockout risk, and uptime for local diagnostics (`ori-cli doctor`). **The developer fallback fires however an unusable default path presents.** One condition reaches the caller as several errnos: `EACCES`/`EPERM` under a non-root account, `ENOENT` where `/run` does not exist as on macOS, `EROFS` where it exists on a read-only filesystem, and `ENOTDIR` where a component is not a directory. Catching `PermissionError` alone meant the fallback written for exactly this case never fired on a developer machine, and the health surface was lost for the life of the process behind a traceback. The set is filtered by errno rather than widened to every `OSError`, because an address already in use is another runtime holding that path and falling back from it would hide the second runtime behind a health surface on a different one; and the fallback still applies only to the packaged default, so a path an operator configured is never silently moved. **A pathname is not an identity, and the socket lifecycle now says so at both ends.** An existing socket file is probed for a listener before it is replaced — only a refused connection proves it stale, and every other outcome including a timeout is read as live, because unlinking a socket a running device serves on is the worse mistake; without that, a second runtime took the pathname from a live first one, which stayed running and unreachable. Binding is transactional past the listener: a failure applying the socket mode closes the provisional server and removes its file, where it previously raised with a live listener nobody held, serving on permissions never applied. And cleanup never removes a socket some process is answering on, whoever created it, so a runtime that stopped listening cannot delete the socket a replacement bound in the interval before its own cleanup ran. A device, inode and creation-time identity narrows it further to the file this server bound, but does not settle it and is not what the guarantee rests on: Linux reuses an inode the moment its file is unlinked, and a handover fast enough to finish inside the filesystem's timestamp granularity was measured producing a byte-identical identity for two different sockets — a divergence macOS does not show, which is why this was found by the hosted runner rather than by a host suite. **A runtime that could not start the socket says so at CRITICAL.** It cannot report itself degraded through the surface that failed, and several conditions have no other reporter — a sensor that stopped measuring, a trust anchor that verifies nothing, a signed field an unsigned source supplied — so from a fleet's side such a device is indistinguishable from one that is not answering. The log line is what distinguishes them; every other surface keeps serving.

## Firmware telemetry verification (evidence Layer 1 consumer)

Status: Implemented. Files: security/firmware/telemetry.py, security/firmware/ingest.py, tests/firmware/test_envelope_vectors_v2.py, security/firmware/controller_profiles.py, tests/firmware/test_controller_profiles.py, gateway/firmware_telemetry.py, state/_firmware.py, tests/firmware/test_telemetry.py, tests/firmware/test_uptime_freshness.py, tests/firmware/test_mqtt.py, tests/firmware/test_fault_v2.py, tests/firmware/test_telemetry_families.py.

Runtime-side verifier and MQTT subscriber for `ori-specs/firmware-telemetry/v1.md`. A topic payload is routed only when it carries exactly one of the five `firmware-telemetry/v2` Layer 1 family keys beside its `signature`, decided on the keys alone, before any inner object is read; anything else is refused with a coalesced WARNING, and the envelope and fault verifiers refuse it again, as `invalid_envelope` once the device's anchor checks pass. Only `envelope` and `fault` are consumed: `maintenance_event`, `result` and `command_result` are not acted on, and no family but `envelope` supervises a device. A manifest may declare `command_results: "firmware-command-result/v1"` and is refused with `invalid_command_results` for any other value; command results themselves are not yet consumed (ori-runtime#482). Provisioning registers a firmware device public key, posture, manifest hash, manifest JSON, and derived channel map in `firmware_device_registry`; operator approval never mutates the pinned capability hash. Ingestion verifies Ed25519 signatures over the exact shared Layer 1 canonical bytes, checks device id, posture, manifest binding, `(boot_id, seq)` freshness, revocation, and channel/type/unit/quality against the accepted manifest before constructing `SensorReading` objects. The freshness advance commits only while the registry still holds the anchor the message was verified against (key, posture, capability hash, channel map, anchor and key epochs); a message whose anchor moved first is verified again against the current one, so an approved rotation or promotion cannot admit a message verified under its predecessor. `readings: []` heartbeat envelopes advance liveness/freshness but never enter reasoning or actions. Signed firmware fault events share the same freshness stream, are recorded in `firmware_fault_events` under the key epoch they were verified against, in the transaction that advances the freshness mark, and never reach skills or action dispatch. A fault object carries its own version: `v` 1 is judged under `firmware-telemetry/v1`'s closed detail sets, `v` 2 under the closed sets of the amendable `firmware-telemetry/v2` draft, which add `rate_limited` to `command_rejected`, list `liveness_authority_failed` under `ingress_degraded` and `command_record_write_failed` under `storage_degraded`; any other `v`, including `2.0` or `true`, is refused, and `rate_limited` at `v` 1 is refused. A `rate_limited` refusal is recorded as a fault and never as an execution. A manifest is registered only when its `device_mode` is one of the four `firmware-telemetry/v2` defines and is the mode its `channels` and `actions` determine (`invalid_device_mode`), and only when it declares a channel (`no_channels`), so `actuator_node` is never registered. An anchor stored before these rules is held to them too, once per anchor and rule revision: an active anchor whose stored manifest fails them has its telemetry and faults refused with the same code, and a pending candidate that fails them is not promoted. Promotion is bound to the candidate that was checked, and in the provisioner to the one whose key the operator confirmed, so a candidate replaced in between is not promoted. Registration, promotion, revocation, reinstatement and re-provisioning each read and write under one `BEGIN IMMEDIATE` transaction, so another connection to the database cannot change what a decision read before its write lands. Registering a manifest that meets the rules and promoting it repairs a failing active anchor. The mode confers no authority and no trust grade. Controller Profiles (`firmware-telemetry/v2`) are implemented: a bridged channel must name its profile by digest and sit on `modbus_rtu` (`controller_profile_missing`, `controller_profile_unexpected`, `invalid_controller_profile`, `invalid_alarm_channel`, and one id to one digest, qualification and record). Profile documents are held from `gateway.firmware_telemetry.controller_profiles_dir` by digest, read once at start; a file that is not a regular `.json` file under 1 MiB, or that fails the grammar or canonical bytes, is listed in health as refused and never stops the start; used only when their held bytes are canonical, valid and agree with the manifest channel, and never fetched from a device. A bridged measurement outside its usable document's range is refused as a producer defect; every bridged reading carries the manifest's profile binding and qualification, which confers nothing. An alarm word never becomes a `SensorReading`, and `refuse_unusable_reading` turns away `controller_alarm_word` and `bitmask` wherever it runs (a local poll reaches the safety registry first, which refuses a `bitmask` unit as a mismatch); its state is a snapshot shown in health as of its reading, unknown on silence past `3 x poll_interval_ms + 30000` on CLOCK_BOOTTIME (CLOCK_MONOTONIC on macOS; no state stands on a platform with neither), on a `sensor_fault` for the channel until a later reading, on any promotion, rotation or revocation (scoped by the promotion transition, which the freshness advance also binds, so a reinstated anchor promoted again starts empty; an approved anchor with no promotion on record never shows a state until it is promoted), on a shared envelope or an out-of-range word, and across a restart. The profile and manifest corpora are vendored and driven through registration, ingestion and the anchor lifecycle in `tests/firmware/test_controller_profiles.py`. The reading envelope at `v` 2 (`firmware-telemetry/v2`) is accepted beside `v` 1: `alg`, the device, the capability hash and the signature are checked first, then `unsupported_version`, `liveness_nonce_at_v1`, `liveness_nonce_missing`, `invalid_liveness_nonce` and `unexpected_field` in that order, then v1's field checks; `envelope-vectors-v2.json` is driven through the ingest gate in `tests/firmware/test_envelope_vectors_v2.py`. `gateway.firmware_telemetry.enabled` subscribes to `ori/fw/+/telemetry` and feeds only accepted readings into the normal `OriEvent` path. Trust grades are receiver-derived (`attested`, `attested_dev`, `rejected`), not firmware-signed; accepted readings preserve their registry-verified posture, development-posture readings remain excluded from insurer-facing export, and legacy/local HAL readings are explicitly labelled `unattested` when they trigger actions.

## Firmware reading age (runtime liveness bound)

Status: Implemented. Files: security/firmware/reading_age.py, security/firmware/liveness.py, security/firmware/ingest.py, reasoning/action_dispatcher.py, runtime/_firmware_wiring.py, runtime/_sensors.py, tests/firmware/test_reading_age_vectors_v2.py, tests/firmware/test_reading_age_presentation.py, tests/firmware/test_liveness_v2.py.

`firmware-telemetry/v2` How Old A Reading Is, at the signing runtime. The liveness table exists wherever firmware commands are enabled, and holds one entry per `v` 2 nonce this process signed, in memory only, on CLOCK_BOOTTIME (CLOCK_MONOTONIC on macOS; no entry on a platform with neither or when the clock cannot be read), usable for one hour inclusive, bounded per device (an hour of messages at the liveness interval) and in total (65,536 entries, whatever the interval), evicting the earliest signing start and then the first nonce in byte order. An accepted `v` 2 envelope whose nonce matches an entry for its device, boot and manifest within the hour takes that signing start, held immutably under the message's key epoch and `(boot_id, seq)`, since a new key epoch restarts those counters; `age_upper = now - signing_start` is computed at each use, never stored, with T read before the monotonic sample so a pause between the reads lengthens A. Health's `firmware_reading_age` shows each device's latest accepted reading by key epoch and `(boot_id, seq)` with its bound as "polled no more than A ago, as of T" or `unbounded`, and each alarm snapshot in `firmware_controller_profiles` carries the same, as a snapshot of the poll. The runtime hands the dispatcher the statement, so the action path reads no provenance; the Tier C approval request's Measured line for a firmware reading reads "not reported by device", followed by the anchored bound when there is one. A restart empties the table, so a reading read back from storage has no bound. The bound dates the device's poll, confers no authority and is not a safety input. `reading-age-vectors-v2.json` is driven through the signer and tracker.

## Firmware command egress

Status: Implemented. Runtime-side producer for `ori-specs/firmware-commands/v1.md`. A command is published once: nothing reissues it automatically, after a failed publication, a `rate_limited` refusal or any command that went unanswered. `gateway.firmware_commands.enabled` is disabled by default and requires raw Ed25519 runtime-command and provisioning-authority seeds from environment variables. Provisioning approvals bind the runtime command public key to one approved firmware device and its accepted capability manifest, then publish retained on `ori/fw/<device_id>/provision`. Commands are signed against the accepted manifest hash, over the command object prefixed by its signing domain `ori.firmware_command.v2` and a NUL (`firmware-commands/v2` Signing Domains; nothing the runtime command key signs is over the bare bytes), consume a strictly increasing per-device `cmd_seq`, and publish non-retained on `ori/fw/<device_id>/cmd`; the signer refuses unknown, revoked, unapproved, out-of-vocabulary, or manifest-unauthorised commands, and commands for a device whose accepted manifest does not declare `runtime_key_domains` (`firmware-telemetry/v2` Runtime Key Domains), before allocating sequence numbers. Such a device's `runtime_commanded` actions are reported unavailable by a WARNING when its manifest is accepted and at each start over a manifest already held, and health names it in `firmware_liveness.undeclared_device_ids` and degrades `status` (runtime-health/v4; the token waits for gateways that accept it). A command is additionally signed only when the target device's active anchor epoch is cross-store confirmed, and a provisioning approval is published only under the same confirmation (see cross-store device anchor confirmation). The `cmd_seq` allocation rechecks revocation, approval, confirmation and the anchor the command was built from in its own commit, and the retained approval is published only after the same check in one read, so a revocation, rotation or promotion landing after the signer's reads stops the command or approval. Bytes of a publication the runtime has reported as failed are never written to the socket afterwards. The publisher hands nothing to a disconnected client, which would queue it; replaces a disconnected client at once with a fresh one; and retires any client that failed a publication, timed out without the broker's acknowledgement (read from `is_published`, since paho's wait returns nothing either way) or was cancelled mid-publication. Retirement shuts the client's socket before anything else, since a graceful disconnect would first write whatever the client still held, and its clients never reconnect on their own, since a reconnect would resend the queue on a new socket. The shutdown is a plain socket call and nothing awaits, so cancellation cannot skip it; the disconnect and loop stop run off the event loop. Bytes written to the socket before the failure was reported may still reach the broker: a missing acknowledgement does not prove nothing was sent. A change committed after the final check also overtakes a publication already in flight, bounded by the publish timeout for commands, approvals and liveness, and without bound for approval bytes emitted by `ori-firmware-provisioner prepare-approval` for later manual publication. A message the broker has received is outside the runtime's reach: revocation does not clear an approval already retained there, or withdraw a command or liveness message held for an offline device's session (ori-specs#287). Reconnect attempts while the broker is down share no backoff (#814).

## Firmware runtime liveness signing and publication

Runtime-side producer for the signed liveness signal in `ori-specs/firmware-commands/v2.md` (Runtime Liveness, published at `v` 2 alone), which is what tells a device whether an authority is alive and watching it and therefore whether its Local Interlock may act alone. Broker connectivity proves a session and nothing about this runtime. Liveness is signed with the same runtime command key the device already pins — no new key material — over the fixed `v` 2 grammar `{boot_id, capability_hash, device_id, nonce, runtime_seq, v}` prefixed by its signing domain `ori.firmware_liveness.v2` and a NUL (`firmware-commands/v2` Signing Domains), only for a device whose accepted manifest declares `runtime_key_domains`, and published non-retained on `ori/fw/<device_id>/runtime` at QoS 1; retention is refused at the call site because a retained message would let a device reconnecting after a runtime death suppress its own backstop for a full expiry window. A signature cannot prove continued supervision (`boot_id` is neither secret nor perishable), so the contract places an obligation on the runtime that the device cannot check: publish only while still receiving. `FirmwareLivenessSupervisor` enforces it — only accepted, authenticated telemetry establishes supervision, a reboot or manifest transition ends it until fresh telemetry arrives under the new identity, and signing refuses an unsupervised device without spending a sequence number. Supervision is in-memory and monotonic so a restarted runtime re-earns it rather than trusting a stored timestamp; `runtime_seq` is the opposite and is allocated durably in SQLite with an explicit commit, since a device holds the last accepted value for its current boot. Its allocation also requires the identity unrevoked, approved and cross-store confirmed at the supervised capability hash, so a revocation stops liveness at once rather than after the in-memory supervision window. A confirmed epoch stays confirmed through an evidence-store outage, so that outage does not stop liveness; a re-promoted, reinstated or quarantined epoch is a grant awaiting confirmation and does, as does an anchor the upgrade backfill marked pending until the coordinator confirms it. Nothing downstream may describe liveness as proof the runtime is receiving; it is proof a key holder claims to be. A scheduler republishes for every currently supervised device, because a signature proves a claim at one instant and only repetition makes it continuous. The interval (`gateway.firmware_commands.liveness_interval_s`, default 15s) is validated against the contract rather than trusted: it must be at least 1s and at most a third of the device's 60s expiry window, so isolated message loss cannot mark a healthy runtime unreachable, and non-finite values are refused because NaN would make every deadline comparison false and stop the loop publishing while it reported itself healthy. An out-of-range configured interval fails startup rather than being clamped. Ticks are scheduled against deadlines, not by sleeping an interval after the previous tick finished, so a slow tick does not push the cadence to `tick duration + interval` and drift toward expiry; devices within a tick publish concurrently under a bounded semaphore with a per-device timeout. The worst-case per-device latency is reported as a function of fleet size rather than as a constant, because the semaphore means devices past `max_concurrent` wait for the batches ahead of them: it is `interval + ceil(devices / max_concurrent) x timeout`, and the configuration exposes the fleet size that bound still holds for, with health reporting when the supervised fleet exceeds it. The per-device timeout is validated so that `interval + timeout` stays under the expiry window, since a timeout larger than the remaining budget would expire the device a slow publication was for. Overrun ticks advance to the next future deadline instead of firing a catch-up burst, since only the newest message matters to a device. The loop drives the command service rather than the transport publisher, so the supervision refusal stays load-bearing; a device that stops sending simply stops appearing in the snapshot, and a per-device refusal, timeout or publish failure is contained so one broken device cannot silence the fleet. A failing tick does not end the loop — ending it would expire every supervised device while the runtime looked healthy — and the scheduler reports `degraded` into the runtime health snapshot, which raises the snapshot's `critical` flag so the condition surfaces through the node heartbeat instead of passing as healthy. Completing a tick is not the same as succeeding at it: a tick that owed publications and delivered none is recorded as a failure, so a broker rejecting or timing out every publication cannot keep health green while the whole fleet expires. Refusals are excluded from that test, because a refused device is one the runtime is no longer supervising, or one whose manifest does not declare the signing domains (named once per device at WARNING), and is meant to lapse. Per-device success times are tracked as well, so a single device failing indefinitely is reported by identity rather than being averaged away by an otherwise healthy fleet. **Partial**: the producer side is complete and the firmware side consumes it, but nothing acts on it yet. Shared golden vectors, the firmware verifier, its ingress path and its broker ACL are all implemented and merged; firmware treats liveness as a shadow observability signal only. `runtime_reachable` on the device is still derived from broker connectivity, so the supervision gap this signal exists to close remains open in practice. Remaining: the safe-maintenance lifecycle (`ori-specs#49`, blocked on duration bounds), hardware-in-the-loop evidence for the broker-alive/runtime-dead case, and the `runtime_reachable` switchover itself (`ori-edge-firmware#68`), which is sequenced last because it changes when a physical backstop is allowed to act. A signing seed this repository publishes is refused wherever one is read: the environment loader every runtime consumer uses, and `read_seed` in the provisioning CLI, which signs approvals without going through that loader. The refused set holds public keys, so both derive the key from the seed and consult one list rather than keeping a second in step; a seed whose key cannot be derived is refused rather than trusted, because a check that cannot be made must not pass. `golden_selfcheck` reads the corpus seed directly and is unaffected (#546). Liveness is published at `v` 2 alone (`firmware-commands/v2` Which `v` the runtime publishes): one message per interval at the next `runtime_seq`, never `v` 1, and an interval whose nonce, signature or publish fails sends nothing in its place; a nonce failure counts as a failed publication, not a refusal. The `v` 2 nonce is 128 CSPRNG bits, replaced if the live liveness table holds it, and is recorded in that table at a signing start read before signing, or not at all when that clock cannot be read, with the message still published (`liveness-vectors-v2.json` driven in `tests/firmware/test_liveness_v2.py`). The runtime does not infer that a device accepts `v` 2: the declaration is the signal. `gateway.firmware_commands.publish_liveness_v2` is retired and refused at config load.

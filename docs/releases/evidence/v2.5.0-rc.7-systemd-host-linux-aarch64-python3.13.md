# health-gated rollback on a systemd host

**Result: every phase exit 0 — install, persist, rollback, persist after the
rollback, uninstall. Nothing tagged. Nothing published.**

This is the run issue #335 asked for: a candidate that installs and activates,
then fails its own post-install diagnosis with the exact
`post_install_health_failed` code, and is rolled back on a real systemd host
with a real reboot on either side of the rollback.

## The failing candidate

`2.5.0-rc.99` is a rollback probe, not a candidate. Its commit is one change on
top of the release under test: the runtime's health snapshot reports
`critical: true` and `status: degraded` unconditionally, with the version
raised so the installer treats it as an upgrade. That is the only way to reach
the rollback path — anything that fails verification, extraction or unit
rendering fails *before* activation and would prove nothing. The version is
one no release will carry, and the commit lives on a branch that is never
merged.

## What was proven

- The failing candidate verifies, installs and activates; its own health
  verification then refuses it with `post_install_health_failed` ("runtime
  reported unhealthy status"), not some other nonzero exit.
- The previous release is restored, the failed release directory is removed
  rather than retained as a selectable version, the unit stays active, and the
  installed doctor reports healthy on the restored release.
- The launcher at `/usr/local/bin/ori`, which resolves the active release at
  execution time, reaches the restored release.
- A reboot after the rolled-back upgrade comes up on the restored release,
  active and enabled — proven against a boot id recorded at the rollback, so
  it is not satisfied by the reboot that followed the original install.
- Uninstall then removes the unit, every managed path and the empty install
  root, retaining only the service account.

The same install, rollback and uninstall phases were rehearsed first on an
Ubuntu 24.04 `aarch64` container running systemd as init
(`linux-aarch64-python3.12`, harness revision 13); the two `persist` phases
cannot run there because a container restart is not a boot.

## What this does not establish

KMS signing custody, the production trust root, publication, authenticated
download and post-publication reverification: the artifacts are
development-signed and were never published. The release under test is the
`v2.5.0-rc.7` preparation commit built with the generic wheelhouse; on
Raspberry Pi hardware that installs without the pin factory staging, so this
run says nothing about GPIO.

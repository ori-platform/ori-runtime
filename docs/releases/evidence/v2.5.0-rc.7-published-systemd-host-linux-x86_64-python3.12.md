## What was proven

- The published checksum passes and the bundle verifies against the production
  key before extraction on a clean host. It installs in system scope with the
  requested identity: healthy, launcher working, unit active and enabled under
  `ori-runtime`, health socket open, and installed doctor clean including code
  integrity on the real venv.
- After a genuine reboot the unit remains active and enabled and doctor still
  reports the release under test.
- The development-signed candidate verifies and activates, then its critical
  health report is refused with `post_install_health_failed` / "runtime
  reported unhealthy status". The installer restores `rc.7`, removes the failed
  candidate, preserves the installed identity, and leaves the service, doctor
  and launcher healthy on `rc.7`.
- A second genuine reboot comes up on the restored `rc.7`, active and enabled.
- Uninstall removes the unit, every managed path, the evidence state, the
  launcher and the install root, retaining only the service account as
  designed. Final verification confirmed `/opt/ori`, `/usr/local/bin/ori` and
  `ori-runtime.service` were all absent.

## What this does not establish

The failing candidate is development-signed by design: a deliberately broken
bundle is never put through the production release key, so this record says
nothing about KMS custody or authenticated download for that artifact.

It establishes only `linux-x86_64-python3.12`. Four other bundles are published
for this candidate and are not certified targets: Raspberry Pi OS Bookworm
`aarch64` with stock Python 3.11, whose GPIO pin factory the runtime does not
stage, and the `x86_64` 3.11 and 3.13 and `aarch64` 3.12 bundles, which are
community compatibility rather than supported platforms.

The host is a virtual machine. It is a real systemd host with genuine reboots,
which is what the runbook requires, and it is not bare metal.

under test is the published, workflow-signed `v2.5.0-rc.7` bundle, installed

## What was proven

- The published rc.7 bundle installs on stock Trixie/3.13 through the
  operator path, with the Pi wheelhouse: `lgpio` staged, the `pyftdi` scripts
  rebound, no `__pycache__` in the release `bin`, doctor clean.
- Installed as an operator would upgrade — no identity flags — the failing
  candidate verifies, installs and activates, and its own health verification
  refuses it with `post_install_health_failed` / "runtime reported unhealthy
  status", which the harness now prints from the installer's report.
- rc.7 is restored, the failed release removed, the unit stays active, the
  installed doctor and the launcher both report rc.7, and the installation's
  identity survives the rollback.
- A reboot after the rollback comes up on rc.7, active and enabled, proven
  against the boot id recorded at the rollback.

## What this does not establish

The failing candidate remains development-signed, as it must. This run did
not repeat the runbook's clean-host install and uninstall phases with the
published bundle: the release was installed as an upgrade of an existing
installation, which is the path a deployed device takes.

# Ori Runtime — v2.4.0 Release Notes

## Release Type

Stable minor release (`v2.4.0`). **Recommended for everyone on v2.3.0.**

This release contains two breaking changes to the `ori-install-linux`
command. See [Migration](#migration) before upgrading automation.

## Compare

`v2.3.0...v2.4.0`

https://github.com/ori-platform/ori-runtime/compare/v2.3.0...v2.4.0

## Summary

v2.3.0 shipped the authenticated installer and could not install on the
platform it named as its primary production target. This release fixes that,
and then fixes the reason nobody could tell what had happened afterwards.

`v2.3.1` was prepared as a hotfix for the first problem and never published;
its three fixes are included here.

**If you are running v2.3.0, upgrade.** If you tried to install v2.3.0 on a
Raspberry Pi and it failed, that was the extraction defect below.

## Release candidates

`v2.4.0-rc.1`, `v2.4.0-rc.2` and `v2.4.0-rc.5` are published tags that produced
no artifacts. All are retained. None was moved or deleted, and none should be
installed — nothing was ever built, signed, or published from any of them.

| Tag | Reached | Failed because |
|---|---|---|
| `v2.4.0-rc.1` | protection preflight, full test matrix | the build compared the whole tag against the packaged version, so no pre-release tag could ever match |
| `v2.4.0-rc.2` | protection preflight, full test matrix | the wheel version and the bundle version were compared as strings, and a candidate spells them differently |
| `v2.4.0-rc.3` | signed, published, exercised on hardware | neither scope could complete an install: system scope checked for its service account too late, and user scope was refused for a property it cannot have |
| `v2.4.0-rc.4` | signed, published, installed on hardware | user scope installed and ran; system scope rolled back because the interpreter's ordinary symlink was misread as writable, and bare `ori doctor` raised on an install root it could not read |
| `v2.4.0-rc.5` | protection preflight | the tag was annotated rather than signed, and a release tag must carry a verified signature; the preflight refused it before anything was built |

`v2.4.0-rc.3` is the first candidate that built, signed, and published. Its
assets remain available and are not replaced. It failed on hardware, which is
what it was published to do.

Two defects surfaced there. A system-scope install stopped with
`service_start_failed: system service user does not exist` — a precondition
that had been checked only after the operator answered every identity prompt
and the installer had built a virtual environment. The installer now creates
that account itself, as a distribution package does — after the bundle is
verified and the values confirmed, and before any package is installed or the
environment is built. A user-scope install then
stopped with `post_install_health_failed: permissions.code`, because v2.4.0
introduced a mandatory code-immutability check without the privilege separation
that makes it satisfiable: under user scope the release and the runtime share
one Unix owner. Sealing the tree read-only would have quieted the check without
creating the boundary, since an owner can always restore write access to its
own files. The check is now mandatory for system scope, where root-owned code
and an unprivileged service account make it real, and an explicit warning under
user scope, where it cannot be.

`v2.4.0-rc.4` installed. A user-scope installation completed, ran, and reported
`13 pass · 3 warn · 0 fail`, including the advisory that user-scope code cannot
be made immutable from the account that runs it. Two defects remained.

A system-scope installation rolled back at post-install diagnostics. The
release was correct — root-owned, unwritable by anyone else — but the execution
guard read the mode of `venv/bin/python` and refused it. Linux reports every
symlink as 0777 whatever it points at, and a virtual environment's interpreter
is always a symlink, so a correct installation was refused by a check reading
permission bits that grant nothing. Replacing a symlink requires write access to
the directory holding it, which is the thing that has to be verified.

That rule now has one definition rather than several. A single path-trust
primitive walks every component from the root, checks ownership everywhere and
write permission only where it means something, follows symlinks one hop at a
time while validating each destination in full, and bounds resolution so a
cyclic or absurdly long link tree ends the check instead of the process. The
root-execution guard, the release's external-symlink admission and the
installer's `useradd` resolution all use it, so the boundaries cannot disagree
about the same path. Trust is the test, not containment: an interpreter that
resolves to `/usr/bin/python3.12` is normal and allowed, provided root alone
controls every step of the way there.

The second defect was in scope detection. `ori doctor` with no `--scope`
inspects both install roots, and a system root left behind by a rolled-back
installation is unreadable to an ordinary account — so the command the installer
itself recommends ended in a traceback. Detection now distinguishes "absent"
from "could not be read": a definitively present installation is selected when
the other root is unreadable, and when nothing can be established the operator
is told to pass `--scope` explicitly. Both command entry points also refuse to
let any inspection failure escape as a traceback.

The first two failures share a different cause. The release pipeline carries two version
vocabularies — SemVer for the git tag, the signature envelope, the bundle
manifest and the artifact name; PEP 440 for the wheel, its metadata and the
version the installer reads back on the device. They agree for every final
release and diverge for every candidate, so no release before this one
exercised the difference.

Both failures also landed in the build job, after the tag was immutable. A tag
cannot be rebuilt, and a tag-triggered run resolves the workflow at its own ref,
so neither candidate could be recovered by fixing `main`.

A candidate now identifies itself consistently:

| | `v2.4.0-rc.3` | `v2.4.0` |
|---|---|---|
| Git tag | `v2.4.0-rc.3` | `v2.4.0` |
| Packaged version | `2.4.0rc3` | `2.4.0` |
| Wheel metadata | `2.4.0rc3` | `2.4.0` |
| Bundle and artifact name | `2.4.0-rc.3` | `2.4.0` |

`-rc.N` is the only accepted pre-release form, and it maps to exactly one PEP 440
spelling. `2.4.0-rc3` is refused rather than treated as a synonym, so one build
can never be published under two identities. Every comparison between the two
vocabularies resolves through a single authority, and the tag is now checked
against the packaged version in the preflight job — before a bundle exists and
before any signing credential is issued.

The final release is its own commit changing the packaged version from a
candidate to `2.4.0`, and runs the full pipeline again. It is not byte-identical
to the last candidate, because the version metadata legitimately differs: the
candidate validates the code and the deployment, and the final run validates the
artifact that ships.

## What was broken in v2.3.0

### The installer could not run on stock Raspberry Pi OS Bookworm

The bootstrap extracted the verified bundle with
`tarfile.extractall(..., filter="data")`. That parameter arrived in Python
3.11.4. Raspberry Pi OS Bookworm — and Debian Bookworm generally — ships Python
3.11.2, so extraction raised `TypeError` after the signature had already
verified. Operators saw a Python traceback, not a stable error code, on the
platform the release notes called primary.

Extraction now writes each already-validated member explicitly. Every member is
still checked for traversal, absolute paths, duplicates, special files, and
setuid bits before anything is written, so this is equivalent to `filter="data"`
and works on every supported interpreter.

### A renamed copy of the bootstrap exited 0 without installing

The bootstrap dispatched on its own filename. Anything not called
`install-linux.sh` fell through to the piped code path, read nothing from
stdin, and exited **0** — a successful-looking no-op, the worst failure mode an
installer can have.

Dispatch is now on execution mode: a readable script file runs itself whatever
it is called, stdin remains the pipe path, and a case with neither a file nor
piped input fails with a stable code.

### Every console script in an installed release was unrunnable

`pip` writes an absolute interpreter path into each console script at install
time. The installer builds the environment in a staging directory and moves it
into its final versioned path, which left every entry point pointing at a
directory that no longer existed. The service was unaffected because its unit
invokes `python -m ori.runtime`, which is why this survived: validation checked
that the runtime could be *imported*, never that an entry point could be *run*.

Interpreters are now rebound after the move and before activation, and
validation executes an entry point rather than stat-ing it.

## What this release adds

### Production capabilities fail closed

Development deployments may still simulate GPIO relay output and degrade when
optional CoAP or local-inference dependencies are absent. Staging, production,
and explicit production-posture enforcement now refuse startup before opening
the state store when a configured GPIO pin or enabled status signal lacks
`gpiozero`, a configured CoAP action or sensor lacks `aiocoap`, or
`reasoning.default_tier: local` lacks `llama-cpp-python` or a readable GGUF
model. The GPIO dependency probe proves importability, not hardware; real
pin-factory initialization remains the hardware proof and aborts hardened
startup on failure. `relay.enabled` gates Tier B/C use, while a configured
`gpio_pin` continues to declare the Tier D path regardless of that flag.

### An `ori` command that exists

v2.3.0 ended a successful installation by telling operators to
`Run ori doctor` — a command that did not exist, in any form, anywhere. There
is now an `ori` console script providing `doctor`, `status`, `install`,
`uninstall`, `config validate` and `--version`, each with help covering
examples, scope behaviour, exit-status meaning, and unattended and JSON
options. The existing specialised entry points are unchanged.

An installation now ends by telling you only what is true: if the launcher
could not be written, it says so; if `~/.local/bin` is not on your `PATH`, it
gives you the exact `export` line; and it names the command only when the
command will actually resolve.

### Diagnostics that run themselves

After activation the installer runs the installed `ori doctor` **by absolute
path**, bound to the installation it just activated. A mandatory failure —
invalid config, wrong runtime identity, inactive service, unreadable config,
unsafe permissions — fails the installation and triggers the existing rollback.
Warnings do not: a user service that will not survive a reboot, and
deliberately disabled optional integrations, are reported and kept.

Doctor classifies every check PASS/WARN/FAIL and reports scope, release
version, install root, active release, config path, data path, health socket,
unit location, service user, and whether the service survives a reboot.

### Scope is a decision, not a default

`--scope` no longer defaults to `user`. Interactive installs present both
options with their consequences and require a submitted answer; unattended runs
require `--scope` and fail before touching the host. The installer never
escalates privilege on your behalf — choosing system scope without root ends
with the exact command to repeat.

Scope is never inferred from whether you used `sudo`. When both a user and a
system installation exist, commands require `--scope` rather than guessing.

### Identity suggested from the host, never invented

Device ID and name are suggested from the hostname, with constraints and
examples shown, and Enter accepts the suggestion. A stock-image hostname
(`raspberrypi`, `localhost`, `ubuntu`) gets a short random suffix, because
otherwise every device flashed from one image shares an identity. Location and
operator contact are **never** suggested — a plausible-looking location in a
fleet report is worse than a blank one.

Collected values are read back for confirmation before anything is written.
Rejected input is never echoed. Unattended runs remain reproducible: no
prompting, and no generated identity unless `--generate-device-id` is passed.

### Prerequisite help you have to ask for

Missing OS prerequisites are reported with the exact packages and the exact
command, and the installer offers to install them — defaulting to **No**.
Declining, cancelling, lacking privilege, or running on an unrecognised
distribution all leave the host untouched and stop with a stable
`prerequisite_install_failed` code and the command to run.

Package names come from a fixed allowlist placed into a fixed argument array;
nothing is passed through a shell. Nothing here resolves Python packages —
runtime dependencies still come only from the authenticated, hash-locked
wheelhouse inside the verified bundle. Unattended runs never prompt and never
mutate the host. Prerequisite checks run only *after* the bundle is
authenticated, so an unsigned or tampered bundle can never reach a package
prompt.

### Human output by default, JSON on request

`ori-install-linux install` now prints a structured human summary with portable
colour, suppressed when output is not a terminal, when `NO_COLOR` is set, or
when `TERM=dumb`. `--json` emits exactly one JSON document on stdout — for
failures too — with prompts and progress on stderr, so automation always
receives valid JSON.

A non-persistent service appears prominently as a warning with its remedy.

### One `ori` command across upgrades

The launcher installed at `~/.local/bin/ori` or `/usr/local/bin/ori` resolves
the active release when it runs, so upgrades and rollbacks take effect without
rewriting it. It is installed inside the install transaction and restored on
rollback. A user-scope launcher refuses to run as root before reaching any
release code, using an absolute `/usr/bin/id` so `PATH` cannot influence the
decision.

Only launchers this installer wrote are replaced or removed; a file you put at
that path yourself is left alone.

## Skill trust boundary hardening

The runtime parses `skill.yaml` and loads `hooks.py`, and is the last layer
before a relay moves. Review of that boundary found that several decisions the
framework treats as authoritative were being taken from the skill file itself.
These are closed here. Full reasoning is in `DECISIONS.md` (2026-08-15).

**Action tiers are now decided by the runtime.** A new action capability
registry records, for every action the runtime can execute, the minimum tier it
may be dispatched at and whether it may serve as a Tier C safe default. A skill
declaring `trip_relay` as Tier A previously reached immediate autonomous
execution; it is now refused at load and raised to Tier C at dispatch. A skill
naming a relay action as its `safe_default_action` — so that refusing a
proposal performed it — is refused as well.

The reverse is also closed. Declaring an action as Tier D does not grant more
authority; it *removes* the approval workflow. A skill with a Tier A trigger
that listed `trip_relay` as Tier D had the relay operate with no operator
involvement. Escalation from a skill's action list is now capped at Tier C.

**Tier D triggers now require first-party provenance**, and absence of that
provenance counts as absence of the grant rather than possession of it. The registry sets a
floor, not a ceiling — within that floor a skill still picks its own tier, which
is intended. Tier D is the exception, because it is the only tier that removes
the operator instead of adding one. A correctly signed community skill could
otherwise declare an always-true Tier D trigger on a relay action and obtain
autonomous physical actuation with every other check passing; a signature proves
who supplied a skill, not that the runtime granted it that authority.

Tier D is therefore accepted only from skills that ship with the runtime,
enforced at load and again at dispatch. **Packaged first-party Tier D skills are
unaffected** — the bundled gas-leak and overcurrent cutoffs behave exactly as
before. This is containment until a capability grant binding skill identity,
trigger, action and permitted maximum tier is specified in `ori-specs`.

**Sensor readings can no longer be shadowed.** `value`, `sensor_id`,
`sensor_type`, `unit` and `quality` were injected with `setdefault`, so a
pre-existing key from skill config or hook output won. A skill could define
`config.value` and decide what a Tier D condition compared against, in either
direction. They are now assigned unconditionally from the event, rejected in
skill config at load, and stripped where hook output is merged.

**Hooks can no longer change the tier.** The trigger tier clamp ran before the
`post_reasoning` hook, which receives the mutable result object. It is now
reapplied after that boundary, including when the hook raises.

**Unknown action tiers are refused** rather than executed as Tier A.

**Manifests are admitted under structural limits.** `skill.yaml` is parsed
before its signature can be verified — it has to be constructed to be
canonicalised — so a hostile or accidentally pathological manifest could consume
disproportionate CPU and recursion during startup, and the 1 MiB byte cap does
not bound what a document expands into. YAML aliases and merge keys are now
refused outright, with depth, node-count and collection-size budgets enforced
while composing. No bundled skill uses an anchor.

These limits apply to **every** manifest, including signed YAML-only community
skills — a signature says who wrote a document, not how much work parsing it
costs. A skill is affected if it references an anchor, nests deeper than 32
levels, or exceeds 20,000 nodes or 1,000 entries in a single collection.

**Accepted manifests are bounded by the work they create.** The parser limits
above bound syntax, not workload. Registration produces one EventBus handler per
trigger × required sensor type, and each schedules a reasoning task on the same
event loop Tier D safety processing runs on — so a structurally valid, correctly
signed manifest could still request tens of thousands of subscriptions and
starve safety processing. Valid provenance does not make a resource-exhausting
skill safe.

Per-skill limits now cap triggers (64), required sensors (32), the trigger ×
sensor product (256), declared actions (64), prompts (64) and config entries
(256). Each trigger's `actions.defaults` list is capped at 16 with a total of
256 references per skill, and repeating an action name within one list is
refused — the elevator dispatches every entry, so a long list is message volume
and sequential work, not just declaration size.

A cumulative budget of 1,024 subscriptions and 64 candidate skills applies
across a whole load, because individually legal skills otherwise add up to an
illegal total — the event loop sees the sum. The skill cap counts **candidates,
not successes**, so invalid manifests cannot be supplied without limit to force
parsing work, and discovery streams the directory rather than materialising it.

The subscription budget counts **active** handlers: unregistration returns
capacity, so ordinary skill reloads are sustainable indefinitely. A reload also
validates the whole plan before removing the previous handlers, rather than
discovering mid-way that the replacement set does not fit.

**Skill names are treated as identity.** Names appear in action records, Tier C
approval messages and operator decisions. Duplicate names within a load are now
refused, a community skill may not adopt a packaged skill's name, and `name`,
`author` and `version` must be strings, are length-bounded, and are rejected if
they contain control characters, Unicode format characters, line separators or
surrogates — U+202E RIGHT-TO-LEFT OVERRIDE changes what an operator reads
without changing what was recorded.

**Inspecting a skill no longer executes it.** Listing and validation went
through the loading path, which imports `hooks.py`. Two non-executing entry
points replace that: `validate_one()` answers "would the runtime activate
this?" and applies every check the runtime applies, and `inspect_one()`
describes a skill for listing without the hook activation policy.
`skills-validate` fails for anything the runtime would refuse.

`skills-list` reports metadata plus an `activation` field for skills that parse
and verify but whose **hooks** the runtime will not activate. It is not a
universal reporting contract: `inspect_one()` still applies parsing, validation,
signature verification and the Tier D provenance rule, so a skill refused by any
of those appears in `errors` without parsed metadata. Widening it would mean
reporting fields read out of a manifest that failed verification, which is not a
trade worth making for a nicer listing.

The `skills-list` and `skills-validate` documents gain two aggregate fields.
`valid` is conjunctive — it is false when any skill fails to parse **or** would
be refused at activation, so automation reading it as "these skills are usable"
keeps getting a safe answer. `activatable` and `unactivatable_count` are added
so a consumer can distinguish a malformed skill from a well-formed one the
runtime will not run, without walking the list.

**Executors cannot be registered for ungoverned actions.** `register_executor()`
raises unless the action has a registry entry, so an action cannot become
executable without also becoming governed. A test parses `runtime.py` and
asserts every executor it registers is in the registry.

### Community hooks are disabled in this release

The in-process hook sandbox has been removed rather than repaired. It filtered
`builtins` by denylist while leaving the object graph reachable, and its import
finder implemented only `find_module` — a protocol removed in Python 3.12, so
on Ubuntu 24.04 it was silently ignored by the import system.

There is no in-process fallback, and the OS-isolated runner is not offered
either — `load_community_hooks()` refuses unconditionally, including on Linux
hosts where seccomp/Landlock is available. `os_sandbox.enabled` and
`os_sandbox.require_for_community` no longer decide whether untrusted hook code
runs. `OSSandboxHookRunner` remains in the tree, unreferenced, as the starting
point for the isolation arc.

A skill that does not ship with the runtime and carries `hooks.py` is refused
entirely rather than loaded with its hooks absent. YAML-only skills are
unaffected by this rule.

Isolated community-hook execution is being specified in `ori-specs` before it
is implemented. **This does not affect any published deployment**: there is no
public Skills Hub, no documented community-skill install path, and system skill
storage is root-owned. The exposure was latent, and is closed before the Hub
opens rather than after.

### Skill provenance is established positively

A skill was treated as first-party if its path was *not* under `~/.ori/skills`,
which classified the operator-managed skills directory beside `ori.yaml`,
temporary directories and removable media as trusted. A skill is now
first-party only if it ships inside the package.

**Operator impact:** a skill placed in your configured `skills_dir` that is not
part of the runtime package now requires a verified `ed25519:` signature,
regardless of `security.skills.require_signed`. That setting previously
exempted such skills from verification entirely. Local unsigned skills outside
the package will not load.

## Migration

Three changes require action if you script the installer.

**Pass `--scope` explicitly.** `install` and `uninstall` no longer default to
`user` scope:

```bash
ori-install-linux install --scope user   --bundle ... --signature ...
ori-install-linux uninstall --scope system
```

**Pass `--json` when parsing output.** `install` now prints a human summary by
default:

```bash
ori-install-linux install --json --scope system --bundle ... --signature ...
```

Both are permitted hardening under the installer compatibility policy recorded
in `DECISIONS.md` (2026-08-14): an ambiguous omitted argument may become
required, and default human presentation may change where machine consumers
have an explicit `--json` contract.

**Drop `--service-user`, or pass `ori-runtime`.** The system service account is
now a constant, and the installer creates it when it does not exist:

```bash
ori-install-linux install --scope system --bundle ... --signature ...
```

The flag is retained and still accepts `ori-runtime`, so an invocation that
omitted it or passed the documented default is unaffected. Naming a different
account is refused with `service_start_failed`. A configurable account name had
to be carried by the unit file, the permission checks, the diagnostics and the
documentation, any of which could disagree about who the runtime is — see
`DECISIONS.md` (2026-08-17).

What this release does **not** do is rename or remove an explicit flag.

Machine-facing output does change here, and this is the release that changes
it. `--json` is new for `install`, and its document is richer than the summary
v2.3.0 printed by default: it adds `install_root`, `active_release`,
`config_path`, `data_path`, `health_socket`, `unit_path`, `service_user`,
`launcher_installed`, `launcher_path`, `diagnostics` and `warnings`, and
`next_step` now reports what is actually true rather than a fixed string.
Failures under `--json` emit a stable error document
(`{"schema_version":1,"ok":false,"error":{"code":...,"detail":...}}`) where
v2.3.0 emitted nothing parseable at all. One stable failure code is added:
`prerequisite_install_failed`.

From v2.4.0 onward that `--json` document is the stable machine contract, and
changing it requires a major version or a versioned schema.

No published release has been consumed by a downstream deployment, so the
practical migration cost is low — but the changes are breaking regardless of
audience, which is why they are stated here rather than folded into the summary.

## Compatibility

Public contracts used by companion repos — the MQTT gateway and export
contracts, and the typed `ori.integration` rule-evaluation boundary — are
unchanged from v1.0.0.

A new stable failure code is added: `prerequisite_install_failed`.

A running runtime does change behaviour in one area: skill loading. Skills
shipped with the runtime are unaffected. Skills you added yourself are affected
if any of the following is true:

| If your skill… | Result |
| --- | --- |
| lives outside the runtime package and is unsigned | no longer loads |
| lives outside the runtime package and has `hooks.py` | no longer loads |
| lives outside the runtime package and declares an `action_tier: D` trigger | no longer loads |
| has a `skill.yaml` that is a symlink, FIFO, or over 1 MiB | no longer loads |
| has a `skill.yaml` that is not valid UTF-8 | no longer loads |
| references a YAML alias (`*name`) or merge key (`<<:`) in `skill.yaml` | no longer loads |
| nests deeper than 32 levels, or exceeds 20,000 nodes or 1,000 entries in one collection | no longer loads |
| declares more than 64 triggers, 32 sensors, or 256 trigger × sensor handlers | no longer loads |
| shares a `name` with another loaded skill, or with a packaged skill | the duplicate is skipped |
| has a non-string, overlong, or control/format-character `name`, `author` or `version` | no longer loads |
| lists more than 16 default actions for one trigger, or repeats an action name in one list | no longer loads |
| declares a physical action below its minimum tier | no longer loads |
| names an actuating action as `safe_default_action` | no longer loads |
| defines `value`, `sensor_id`, `sensor_type`, `unit` or `quality` in `config` | no longer loads |

Each refusal is logged at startup with the skill directory and the reason, and
the other skills continue to load — except where a budget is exhausted, in which
case later skills are skipped and that is logged too. If you maintain your own
skills, check the runtime log after upgrading. The `skills-list` and
`skills-validate` bridge commands apply the same checks without executing
`hooks.py`; a refused skill appears under `errors` with its directory and
reason.

These are deliberate: every one of them was a path by which a skill file could
take or influence physical action authority the Action Tier Framework is meant
to hold.

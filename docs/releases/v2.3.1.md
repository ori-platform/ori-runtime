# Ori Runtime — v2.3.1 Release Notes

## Release Type

Stable patch release (`v2.3.1`). **Recommended for everyone on v2.3.0.**

## Compare

`v2.3.0...v2.3.1`

https://github.com/ori-platform/ori-runtime/compare/v2.3.0...v2.3.1

## Summary

v2.3.0 shipped the authenticated installer. Distro evidence then found three
defects in it, two of which prevent installation outright on the platform
v2.3.0 named as its primary production target. This release fixes all three and
corrects the support policy that let the gap through.

**If you are running v2.3.0, upgrade.** If you tried to install v2.3.0 on a
Raspberry Pi and it failed, that was this.

## What was broken in v2.3.0

### The installer could not run on stock Raspberry Pi OS Bookworm

The bootstrap extracted the verified bundle with
`tarfile.extractall(..., filter="data")`. That parameter arrived in Python
3.11.4. Raspberry Pi OS Bookworm — and Debian Bookworm generally — ships Python
3.11.2, so extraction raised `TypeError` after the signature had already
verified. Operators saw a Python traceback, not a stable error code, on the
platform the release notes called primary.

Extraction now writes each already-validated member explicitly, matching what
`ori/security/release_bundles.py` has always done. Every member is still
checked for traversal, absolute paths, duplicates, special files, and setuid
bits before anything is written, so this is equivalent to `filter="data"` and
works on every supported interpreter.

### A renamed copy of the bootstrap exited 0 without installing

The bootstrap dispatched on its own filename. Anything not called
`install-linux.sh` fell through to the piped code path, read nothing from
stdin, and exited **0**. An operator who saved the script under another name
got a successful-looking no-op — the worst failure mode an installer can have.

Dispatch is now on execution mode: a readable script file runs itself whatever
it is called, stdin remains the pipe path, and a case with neither a file nor
piped input fails with a stable code instead of exiting quietly.

### Every console script in an installed release was unrunnable

`pip` writes an absolute interpreter path into each console script at install
time. The installer builds the environment in a staging directory and moves it
into its final versioned path, which left every entry point —
`ori-install-linux`, `ori-runtime`, `ori-config-install`, `ori-phone-doctor`,
`ori-firmware-provisioner`, `ori-inverter-profile-doctor` — pointing at a
directory that no longer existed. The service was unaffected because its unit
invokes `python -m ori.runtime`, which is why this survived: validation checked
that the runtime could be *imported*, never that an entry point could be *run*.

Interpreters are now rebound after the move and before activation. Only regular
executable files whose shebang references the known staging interpreter are
rewritten; symlinks, unexpected staging references, and malformed shebangs are
refused. Modes are preserved, rewritten files and the directory are fsynced, and
a failure deletes the unusable release while leaving `current` and the running
service untouched. Validation now executes an entry point rather than stat-ing
it, so this class cannot pass validation again.

The relocated environment is generated locally from the authenticated,
hash-locked wheelhouse. It is not part of the signed artifact, so rebinding it
alters nothing that was signed; the bundle manifest still governs every verified
byte.

## Supported platforms

Production support is now expressed as tested platform tuples rather than one
global interpreter version. A primary Raspberry Pi target cannot honestly
require a non-stock interpreter while claiming a straightforward authenticated
bootstrap.

| Platform | Architecture | Python | Status |
| --- | --- | --- | --- |
| Raspberry Pi OS Bookworm | `aarch64` | 3.11 (stock) | Production-supported |
| Ubuntu 24.04 | `x86_64` | 3.12 (stock) | Production-supported |
| Other published bundles | `x86_64`, `aarch64` | 3.11, 3.12 | Community compatibility |

Bundles are still built and signed for all four targets; a signature attests
that Ori published those exact bytes, which is a different claim from a support
commitment.

Fedora is deferred compatibility work. Current releases ship Python 3.13, for
which no bundle exists, so the bootstrap reports `unsupported_target`. Adding a
3.13 artifact needs full dependency and runtime validation rather than a hurried
build; Fedora also provides a separate `python3.12` package that a future
evidenced tuple can build on.

## Compatibility

No behaviour changes to an installed and running runtime. Public contracts used
by companion repos — the MQTT gateway and export contracts, and the typed
`ori.integration` rule-evaluation boundary — are unchanged from v1.0.0.

Upgrading from v2.3.0 repairs the entry points as part of the normal install
transaction; no manual repair is needed.

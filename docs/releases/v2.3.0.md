# Ori Runtime — v2.3.0 Release Notes

## Release Type

Stable runtime release (`v2.3.0`) — additive minor release. No breaking
Python-call changes.

## Compare

`v2.2.0...v2.3.0`

https://github.com/ori-platform/ori-runtime/compare/v2.2.0...v2.3.0

## Summary

Ori Runtime v2.3.0 makes installation itself an authenticated operation.

Until now, getting the runtime onto a Linux device meant trusting whatever
bytes arrived and whatever a script did with them. A device that reasons about
current draw and can open a contactor deserves better than that: if the
installation path is unauthenticated, every safety property above it rests on
an assumption nobody checked. This release closes that gap end to end — from
an immutable, KMS-signed release artifact through to a running, health-gated
systemd service that cannot be silently modified by the account it runs as.

The contract is `ori-specs/runtime-release-bundle/v1`. Nothing installs unless
its signature verifies against a key whose public half is pinned in this
repository and normatively recorded in the spec, and whose private half has
never left AWS KMS.

## Authenticated Installation

### Signed release bundles

- Deterministic offline bundle construction with exact post-extraction
  manifests, reproducible from the release tag.
- Purpose-bound Ed25519 key registry packaged in the wheel and pinned by
  `ori-specs#63`; bundles name a `key_id` and can never supply key bytes.
- Signature, digest, size, version, and target are all verified **before** the
  archive is inspected, so unauthenticated bytes are never unpacked.
- Bounded safe extraction: member counts, path traversal, duplicate and
  case-folded collisions, setuid bits, and special files are all rejected.

### Transactional installer

- `ori-install-linux` accepts a local bundle and detached signature, verifies
  both, then performs a single transaction: prepare an isolated environment
  from the hash-locked wheelhouse with no package-index access, validate it,
  activate atomically, restart, health-gate, and only then enable boot
  persistence.
- Any failure rolls back — the previous release is restored, its config and
  unit are put back, and the service is restarted against them. A first
  install that fails leaves nothing behind.
- Downgrades require explicit approval. Reinstalling the same version is
  idempotent and still re-verifies health.

### Service identity and permissions

- User and system systemd profiles are rendered separately and never mixed: a
  user unit carries no `User=`, a system unit carries an unprivileged one, and
  the rendered unit is checked against the profile before installation.
- System installs apply a discretionary access model where verified code stays
  root-owned and read-only to the service, and only the data directory is
  writable by the service identity. The runtime can read its config and create
  its health socket; it cannot modify the code it executes.
- Boot persistence is reported honestly. System units are confirmed enabled;
  user units report whether lingering is configured rather than implying
  persistence that does not exist.

### Config and health

- Config generation is minimal, validated by the runtime's own bridge before
  installation, and never collects credentials. Operator-supplied identity
  values are checked for control characters and interpolation syntax.
- Post-install health is verified through the runtime's own health socket with
  a bounded deadline, matched against the configured device identity, and
  fails fast on a critical runtime rather than waiting out the timeout.

### Authenticated bootstrap

- `install-linux.sh` downloads an explicit immutable version from the approved
  GitHub HTTPS origin, permits redirects only to GitHub-controlled asset hosts,
  and verifies the KMS-backed signature before any release content is extracted
  or executed.
- Requires Bash, Python 3.11 or 3.12, and OpenSSL 3 or newer. Older or missing
  OpenSSL is reported as `crypto_unavailable` and never as a bad signature.
- The residual trust boundary is documented rather than papered over: the
  bootstrap cannot authenticate itself, so a checksum is published beside it
  for the high-assurance path.

## Protected Release Publication

Releases are built, signed, published, and reverified by a tag-triggered
workflow rather than by hand.

- Repository protections are proved before anything is built: a
  reviewer-gated signing environment that refuses self-review and admits only
  version tags, and an active tag ruleset that blocks updates and deletions.
- The release ref must be a verified annotated tag resolving to the built
  commit, so a signed tag is an enforced invariant rather than an instruction.
- Signing happens only from the protected environment, which authenticates to
  AWS through short-lived OIDC federation scoped to that environment. The
  workflow accepts no static AWS credentials — it passes only a role to assume
  — so no key material is present in the pipeline itself.
- Publication is draft-first and never confers `Latest`. A release earns it
  only after the published bytes are re-downloaded from the public origin and
  reverified against the packaged trust anchor.
- A release that cannot be proved immutable is deleted rather than left
  publicly mutable; a release that fails public reverification is preserved for
  forensics, quarantined, and never promoted.

## Supported Targets

Bundles are built, signed, and published for four targets:

| Target | Status |
| --- | --- |
| `linux-x86_64-python3.12` | Production-supported |
| `linux-aarch64-python3.12` | Production-supported |
| `linux-x86_64-python3.11` | Community compatibility |
| `linux-aarch64-python3.11` | Community compatibility |

All four are signed and verifiable — a KMS signature attests that Ori published
those exact bytes. Production support and distro evidence target Python 3.12;
the 3.11 targets are tested and signed but sit outside the production support
commitment.

Raspberry Pi OS Bookworm is the primary production target. Bullseye is not
supported: it ships OpenSSL 1.1.1, which cannot perform the Ed25519
verification the bootstrap requires.

## Compatibility

- No breaking Python-call changes. Public runtime contracts used by companion
  repos — the MQTT gateway and export contracts, and the typed
  `ori.integration` rule-evaluation boundary — are unchanged from v1.0.0.
- Existing deployments are unaffected: the installer is a new path onto a
  device, not a change to how an installed runtime behaves.

v3.0.0 remains reserved for the Rust Tier D authority transition behind the
recorded shadow-mode exit criteria.

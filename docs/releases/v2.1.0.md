# Ori Runtime — v2.1.0 Release Notes

## Release Type

Stable runtime release (`v2.1.0`) — additive minor release with documented
Python-call migration requirements.

## Compare

`v2.0.0...v2.1.0`

https://github.com/ori-platform/ori-runtime/compare/v2.0.0...v2.1.0

## Summary

Ori Runtime v2.1.0 adds the runtime side of an attestable physical-edge trust
path. It verifies signed Verity Layer 1 firmware telemetry and faults, binds
physical commands to approved capability manifests, records input provenance
in Tier C/D evidence, and provides an authenticated local service for
per-device MQTT certificate provisioning.

This release does not move physical authority into the gateway or firmware.
Runtime policy continues to own Tier B/C/D authority. Firmware remains Verity
Layer 1 and its bounded Local Interlock is not Tier D. The gateway preserves
and projects evidence fields without interpreting or granting authority.

v3.0.0 remains reserved for the Rust Tier D authority transition behind the
recorded shadow-mode exit criteria.

## Security and Trust-Path Additions

### Signed Layer 1 ingestion

- Verifies firmware capability manifests, telemetry envelopes, heartbeats, and
  bounded fault events against the shared canonical JSON and Ed25519 contract.
- Enforces `(boot_id, seq)` freshness, closed contract vocabularies, posture
  claims, device identity, capability hashes, and approved anchor epochs.
- Preserves signed input posture and Layer 1 source identity through action
  logs, gateway export, and Tier C/D evidence.
- Uses atomic evidence freshness when the pinned evidence artifact provides
  that surface; verification failure remains a visible evidence gap and never
  silently falls back to weaker signing.

### Anchor lifecycle and cross-store confirmation

- Adds append-only anchor history and transition audit.
- Registration preserves revocation, refuses silent key replacement, and
  stages same-key manifest changes as pending candidates.
- Adds explicit `reinstate` and `reprovision` operations.
- Makes anchor authority effective only after the runtime and evidence stores
  confirm the same `anchor_epoch_id`.
- Keeps telemetry freshness per key epoch while `cmd_seq` remains monotonic per
  device across rotations.

### Firmware command egress

- Signs commands against the accepted capability manifest.
- Requires an approved, cross-store-confirmed active anchor.
- Refuses unknown, revoked, unapproved, replayed, out-of-vocabulary, and
  manifest-unauthorised commands before granting physical work.

### MQTT device certificate provisioning

- Adds the runtime-owned provisioning-authority signer and response verifier
  for `ori-specs/firmware-mqtt-provisioning/v1.md`.
- Adds a P-256 client-certificate workflow with device-bound CSR proof,
  minimal client-auth leaf issuance, exact certificate fingerprinting, and
  broker identity validation.
- Adds a peer-authenticated local operator service. The running runtime alone
  loads the provisioning-authority seed and CA private key; clients receive
  only signed public messages and public certificate metadata.
- Persists request correlations and an append-only audit so restart,
  concurrent revocation, or promotion cannot silently change authority.
- Enforces valid MQTT broker ports before any workflow mutation.

## Evidence Improvements

- Emits the dedicated `SAFETY_ACTION_EXECUTED` vocabulary when supported by
  the pinned evidence artifact.
- Exposes public protocol identifier `evidence.v1` without exposing private
  artifact identity.
- Records `input_attestation_grade`, `input_posture`, and Layer 1 source
  freshness in action evidence and gateway exports.
- Attributes evidence-store anchor promotion to the authenticated approval
  actor and reason.

## Community Skill Signature Hardening

- Separates the canonical-manifest signature verified by runtime from the
  detached exact-artifact signature used by SDK, CLI, and Skills Hub before
  extraction.
- Rejects duplicate/non-string YAML mapping keys, cycles, non-JSON values,
  NaN, infinity, non-canonical base64, wrong key/signature lengths, and
  cross-profile substitution.
- Pins the shared `ori-specs/signing/vectors-v1.json` corpus at SHA-256
  `13832babac98468ddd368aafd04c5140bba771f568500c50d4bac60c8588fddc`.

Detached artifact verification remains a downstream installer/Hub
responsibility; runtime remains a manifest verifier rather than a package
installer.

## Breaking Python-Call Changes

The architectural and wire contracts remain within v2, but callers of the
Python provisioning APIs must migrate:

- `FirmwareTelemetryGate.approve_device()` and `revoke_device()` require
  keyword-only `actor` and `reason`.
- Store-level `approve_firmware_device()` and `revoke_firmware_device()`
  require the same attribution.
- Blank attribution fails before state mutation.

Operator CLI changes:

- `ori-firmware-provisioner approve` requires `--reason`.
- `--actor` is removed. The authenticated operating-system principal supplies
  authority attribution.
- Optional `--actor-label` is annotation only and never replaces the
  authenticated principal.

Example migration:

```python
await gate.approve_device(
    device_id,
    actor="alice@ops",
    reason="bench bring-up",
)
await gate.revoke_device(
    device_id,
    actor="alice@ops",
    reason="key compromised",
)
```

## Registration Behaviour Changes

- Revoked identities return `device_revoked`; registration does not clear
  revocation.
- Changed keys return `key_change_requires_reprovisioning`.
- Same-key manifest changes become pending candidates and do not replace the
  active capability surface.
- `reprovision` refuses `same_key_not_a_rotation` and `key_epoch_reused`.
  These refusal codes are part of the current shared provisioning contract.

Existing databases migrate automatically. Approved anchors remain active,
revoked anchors remain revoked, and other legacy rows become pending without
granting new authority.

## Cross-Repository Alignment

- `ori-specs` defines the Layer 1, command, provisioning, lifecycle, evidence,
  and two-profile skill-signing contracts used here.
- `ori-edge-firmware` implements the corresponding Layer 1 signer, command
  verifier, and MQTT provisioning verifier/service. Its retained-anchor
  persistence, concrete local delivery adapter, and hardware proof remain
  follow-up work.
- `ori-gateway` preserves `attestation_status`, `attestation_seq`,
  `input_attestation_grade`, and `input_posture` as projection fields.
- `ori-verity` supplies the pinned private evidence surface and remains outside
  certificate issuance.

## Explicit Non-Goals

- No Rust Tier D authority flip; that remains v3.0.0.
- No gateway, firmware, perception model, or evidence score gains runtime
  authority.
- No claim of completed hardware-in-the-loop proof.
- No claim that `sealed_flash` is hardware isolation.

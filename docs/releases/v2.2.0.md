# Ori Runtime — v2.2.0 Release Notes

## Release Type

Stable runtime release (`v2.2.0`) — additive minor release. No breaking
Python-call changes.

## Compare

`v2.1.0...v2.2.0`

## Summary

Ori Runtime v2.2.0 adds the runtime side of **signed liveness**: a periodic,
device-bound, freshness-bounded statement that an authority is alive and
watching a given firmware device.

The gap it closes is one a broker cannot: MQTT connectivity proves a session,
not that a runtime exists behind it. A runtime that dies behind a live broker
leaves a device connected and unsupervised while its Local Interlock backstop
stays suppressed — the backstop does not act because nothing upstream appears
to be missing. Liveness makes that condition observable and, once firmware
consumes it, actionable.

This release publishes the signal. It does **not** change what any device does
with it. Firmware still derives `runtime_reachable` from broker connectivity;
the switchover is tracked in `ori-edge-firmware` and gated behind
hardware-in-the-loop evidence.

v3.0.0 remains reserved for the Rust Tier D authority transition behind the
recorded shadow-mode exit criteria.

## Runtime Liveness

### Signing

- Signs the fixed grammar `{boot_id, capability_hash, device_id, runtime_seq,
  v}` per supervised device.
- `boot_id` and `capability_hash` are the **device's**, learned from the
  accepted telemetry that established supervision — the runtime does not
  allocate them. A reboot or manifest transition ends supervision until fresh
  telemetry arrives under the new identity.
- `runtime_seq` is the **runtime's** durable per-device sequence, allocated in
  SQLite with an explicit commit. It is not the Layer 1 telemetry `seq`; the
  two streams are independent.
- Uses the same runtime command key a device already pins for commands, so no
  new fleet authority is introduced.
- Freshness needs no device clock: firmware evaluates `(boot_id, runtime_seq)`
  against the last value it accepted for its current boot, and gaps are
  expected rather than diagnostic.

### Publication

- A scheduler publishes on a fixed cadence to each supervised device's own
  topic, never retained. A retained liveness message is the broker asserting,
  on behalf of a runtime that may since have died, exactly the claim the signal
  exists to make unforgeable.
- Publication runs under a bounded semaphore with a per-device timeout, so one
  slow device cannot delay the fleet indefinitely.
- Scheduling is deadline-based rather than sleep-after-work, so the real cadence
  does not drift into `tick duration + interval`.
- `max_device_publish_latency_s(device_count)` reports the worst-case wait for
  one device as a function of fleet size, and `supported_device_capacity`
  reports how many devices a configuration can carry while every one of them
  stays inside the expiry window. Both are exposed rather than assumed, because
  a constant would be a false claim.

### Constants

- Publish interval 15 s, supervision window 45 s, expiry window 60 s, boot
  grace 90 s.
- The publish interval is validated on construction against a derived ceiling
  of `expiry / 3`. A configuration whose interval exceeds it is refused at
  startup rather than allowed to produce devices that expire between ticks.

### Configuration

- `gateway.firmware_commands` is now documented in `ori.yaml.example`,
  including `liveness_interval_s`. Every key the composition root reads is
  listed with its default and its bounds.
- Liveness deliberately has **no separate enable flag**: command authority and
  its supervision assertion are one operational posture, not two switches. A
  runtime that commands a device but never asserts it is watching is the exact
  condition this signal exists to make visible.

## Fault Vocabulary

- Accepts the `storage_degraded` fault code from firmware, which reports a
  device that could not keep a durability guarantee.
- Enforces the closed `detail` vocabularies per fault code. A detail outside
  its code's set is rejected rather than recorded, so a receiver cannot be
  taught new meanings by a device.

## Cross-Repository Alignment

- The liveness wire format, its constants, and its golden vectors are owned by
  `ori-specs/firmware-commands/v1.md`. This runtime consumes that corpus rather
  than generating expectations from itself.
- `ori-edge-firmware` implements the verifier and reports a shadow observability
  state, but does not yet gate interlock autonomy on it.
- The corpus is digest-pinned and byte-identical across consumer repositories.

## Explicit Non-Goals

- **No change to firmware behaviour.** `runtime_reachable` is still derived
  from broker connectivity on the device; this release only publishes the
  signal that will replace it.
- No claim that signed liveness is proven end to end on hardware. The
  broker-alive/runtime-dead case remains an open hardware-in-the-loop gate.
- No Rust Tier D authority flip; that remains v3.0.0.
- No gateway, firmware, perception model, or evidence score gains runtime
  authority.
- No claim of completed hardware-in-the-loop proof.
- No claim that `sealed_flash` is hardware isolation.
